### Data Diversity Investigation

User asked to validate diverse data feeding. Found a major bottleneck:

**Stats (1000 epochs × 400 steps × 256 batch, 17 slots)**:
- **Only 6.3% of available data used** — 17 segments out of 270 runs available
- **23 passes through each segment** — model memorizing not generalizing
- **75% input overlap between consecutive samples** (sequential cursor stride=1, window=64)

Two compounding issues:

1. **`max_runs_per_group=1`** in pool config — only loads 1 run per date range, ignoring the other ~15 asset-set variations per period. Easy fix: bump to 10+.

2. **`SegmentPool.sample_positions()` uses sequential cursor with stride=1** — designed for Phase 1 episode scanning, terrible for Phase 2 random batch sampling. Documented as **TASK_720** for future fix (replace with random uniform sampling).

### Quick Fix Applied

Added CLI args to `train_phase2.py`:
- `--n-slots` (default 17)
- `--max-runs-per-group` (default 1, recommend 10)

`max_runs_per_group=10` keeps memory at ~14GB but cycles through 10x more unique segments (170 instead of 17). Within-segment sequential issue remains (TASK_720) but the segment-level diversity boost should be the bigger lever.

### Key Insight from This Session

Don't trust per-step classification accuracy as a proxy for trading performance. Phase 1 had 56% balanced accuracy and lost 154%. Stage B has 33% accuracy and loses 5.75%. The model that "gets fewer steps right" but **only acts on high-confidence opportunities** is dramatically better. MCTS naturally produces this behavior by being conservative when value estimates are uncertain.
