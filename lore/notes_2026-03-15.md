## Session 33 — Crash Recovery + TASK_710 Design

### MCE Crash (not OOM, not PCIe)

System crashed overnight. Initial suspicion was OOM, actual cause was Machine Check Exception on CPU 9:
```
mce: [Hardware Error]: CPU 9: Machine Check: 0 Bank 0: baa00000000c0135
PROCESSOR 2:a20f12 TIME 1773526862 SOCKET 0 APIC 3 microcode a201213
```
Plus `sde` disk I/O errors before crash. This is on the **new motherboard** — not the old PCIe instability issue. Could be CPU cache, memory controller, or microcode related. Worth monitoring.

### OOM Root Cause Found

While investigating crash, discovered the real problem: TASK_707's period cycling was loading **all 270 runs** into RAM at startup. Each HistoricalMarket is ~316MB → 270 × 316MB = **81GB**. System has 45GB. This is what triggered the crash.

The 270 runs come from 18 date ranges with multiple asset subsets per range (1-27 runs each, for different 64-asset selections from larger asset pools).

### Quick Fix: Lazy Loading (committed)

Changed `train_easy.py` to lazy-load one period at a time instead of preloading all 270. RAM usage dropped from ~81GB to ~316MB. Training resumed and is running stable at ~270s/epoch.

Changes:
- `OnTheFlyGenerator`: added `_load_period()` method, `period_specs` + `db_path` params
- `advance_period()`: frees previous market, loads next from disk (~10s)
- Removed preload-all loop from main setup section
- Val generator also lazy-loads, offset by half

### Critical Problem: No Linear Coherency

Lazy loading fixed OOM but exposed a deeper issue. Each epoch:
1. Loads a fresh HistoricalMarket (cursor resets to 0)
2. Samples ~400 batches from first ~400 windows
3. Destroys market, loads next

Model only ever sees the beginning of each segment. 258k timestamps per segment, training on <1% per visit. Runs sharing the same date range (e.g., P197-P200 all `2024-03→2024-08`) all restart from timestamp 0.

### TASK_710: Segment Pool Design

Designed a SegmentPool to replace both the OOM preload and the non-linear lazy load:

- **6 active segments** in RAM (~1.9GB), each from a different date range
- **Linear cursor** per segment — walks sequentially through timestamps
- When segment exhausted → replace with next run from same date range (same regime, different assets)
- When date range fully exhausted → pick new date range
- One pass through all data: 270 segments × ~258k = ~70M steps. No reshuffling.

Full spec: `tasks/TASK_710_SEGMENT_POOL_LINEAR_TRAINING.md`

### Training Status

Training running with lazy-load fix (pre-TASK_710):
- Epoch ~5598, agreement 82-83%, AR 35-37%
- Stable but not linearly coherent — TASK_710 will fix this

## Session 34 — TASK_710 Implementation

### TASK_710: SegmentPool — DONE

Implemented `SegmentPool` class in `train_easy.py`. Replaces both the OOM preload (TASK_707) and the non-linear lazy load.

**New class: `SegmentPool`**
- Groups 270 period specs by date range → 18 regime groups
- 6 concurrent slots in RAM (~1.9GB), each from a different date range
- Linear cursor per slot, stride = window_length/2 (50% overlap)
- Round-robin slot selection for interleaved regime diversity
- Rotation: exhausted segment → next run in same group (same dates, different assets) → new group when group done
- Training completes when all slots empty (one full pass through ~70M timestamps)

**Changes to `OnTheFlyGenerator`:**
- New `segment_pool` param; when set, `_refill_buffer()` calls `pool.get_window()` instead of `hm.get_window_random()`
- Handles pool exhaustion gracefully (returns early, resets sample counts for re-sampling)
- `self.historical_market` set to pool as truthy sentinel (keeps existing branch routing working)

**Changes to `train_epoch()`:**
- Skips `advance_period()` when SegmentPool active — pool handles rotation internally

**Changes to `main()`:**
- `--periods-file` now creates SegmentPool (train: 6 slots, val: 2 slots with reversed group order)
- Pool exhaustion = training stop → saves `phase1_pool_complete.pkl`
- Pool status logged every 10 epochs

**Key properties:**
- RAM: ~1.9GB (6 × ~316MB) — was 81GB (preload) or ~316MB (lazy, <1% coverage)
- Coverage: 100% of all timestamps in one pass
- I/O: ~270 segment loads × ~10s = ~45 min total, spread across training
- Backward compatible: single `--db-path` mode and non-historical modes unchanged

### TASK_712: All Regimes as Parallel VEnvs — DONE (multiple iterations)

**Problem:** Value MSE oscillates 0.05↔11.0 because model only sees a few regimes at a time. When slots rotate, value distribution shifts → MSE spikes. Root cause of benchmark MSE ~1160.

**Iteration 1 — max_runs_per_group=3 (WRONG)**
Initial attempt capped at 3 runs per group (270→48 segments). Consumption math was wrong (estimated 102 windows/epoch, actual was **2,040**). Pool exhausted in ~25 epochs (1.9 hours), then crashed on buffer empty. Fixed buffer-empty crash with sample count reset before refill.

**Iteration 2 — No cap, pool cycles (WRONG)**
Removed run cap (all 270 segments), made pool cycle indefinitely instead of exhausting. But tiny segments churned I/O: P17 (2 assets, 10k timestamps) reloaded from disk every ~0.4 epochs — reached pass 73 in a few hours. Each reload = ~40s of SQLite + forward-fill for 43 windows of mostly-duplicate data.

**Iteration 3 — Cursor reset + skip tiny periods (FINAL)**

Three fixes applied:

1. **Cycle indefinitely**: When a group exhausts all runs, wrap to run 0. `is_exhausted` always returns `False`. Pool runs until `--epochs` is reached.

2. **Cursor reset for single-run groups**: Instead of free + reload from disk, just reset `cursor=0`. Eliminates I/O churn for small groups.

3. **Skip tiny periods**: `min_assets=32` filter drops periods where assets < 32 (too much cyclic-pad duplication). Only P17 (2 assets) gets skipped.

**Final config:**
- 17 slots (one per valid date range), 269 runs total
- All regimes active simultaneously — every batch mixes all market conditions
- Pool cycles: walks linearly through each group's runs, wraps when done
- RAM: ~5.0GB train + ~1.8GB val
- No exhaustion — runs indefinitely for 10,000+ epochs

**Consumption math (corrected):**
- Buffer=16, samples_per_episode=200, batch_size=1024
- Each episode gets 10 visits of 20 samples → 200 total → exhausted
- 400 steps/epoch × 51 visits/step = 20,400 visits/epoch
- 20,400 / 10 visits per episode = **2,040 episodes (windows) consumed per epoch**
- 269 runs × ~1,057 windows/run = ~284k windows per full pass = ~139 epochs per pass
- Pool cycles, so training continues indefinitely with fresh asset diversity each pass

### Milestone Checkpoint Bug Fix

Tiered checkpoint cleanup (TASK_144) was deleting milestone checkpoints. Root cause: saves happen at `(epoch+1) % save_every == 0` (epochs 6299, 6304...) but milestone check was `epoch % 100 == 0` (6300, 6400...). Off-by-one: 6300 was never saved, so it could never be kept. Fix: keep saves within `save_every` distance of a milestone boundary.

### AR Ratchet

Added monotonic AR ratchet to TASK_708 MSE feedback. `ar_high_water` tracks highest AR ever reached. MSE feedback can only push AR higher, never lower. Prevents MSE spikes from dropping AR back after stabilization. AR reached 100% by ~E6300.

## Sessions 35-36 (2026-03-16 to 2026-03-18) — Benchmark Audit

### Benchmark Plateau E5399→E6799

1400 epochs of training with no benchmark improvement:

```
E5399: bal_acc=44.8%, alpha=-0.31, beats=6/6, vmse=292.6
E6799: bal_acc=49.3%, alpha=-0.53, beats=2/6, vmse=291.5
```

All metrics flat. 0/6 positive alpha across ALL benchmarks ever.

### Benchmark Pipeline Audit

Audited `tools/benchmark_easy.py` to find train↔benchmark gap.

**Finding 1: Value MSE (291) is a metric bug, not a model bug.**
Benchmark measures remaining PnL over 10,000-step trajectories (range 0-587). Training measures over 400-step windows (range 0-5). Completely different scales. The 291 number is meaningless — the value head can't predict 10k-step horizons when trained on 400-step windows.

**Finding 2: The real problem is trade agreement.**

| Metric | Training | Benchmark |
|--------|----------|-----------|
| agree_trade | 74-77% | 12-33% |
| agree_hold | 96% | 94% |
| balanced_acc | 85-87% | 48-49% |

The model matches holds perfectly but places trades on wrong assets. Per-period breakdown:
- Bull: 32.8% trade agree, oracle trades 2.7%, model trades 7.2%
- Sideways: 12.3% trade agree, oracle trades 2.0%, model trades 3.2%
- Bear: 17.9% trade agree, oracle trades 2.9%, model trades 6.1%

Model trades MORE than oracle but at wrong assets/times. It learned "this is a trade situation" but not "WHICH specific asset at THIS moment."

**Finding 3: Benchmark inference pipeline is correct.**
34-channel observations, sequential AR rollout with model's own state, same position stepping logic as training. No mismatch in how the model is called.

### Root Cause: No Trade Quality Signal

Pure imitation learning treats all trades equally. A +3% trade and a +0.01% trade get the same gradient. The model can't learn that cross-asset signal X means "trade asset 7 specifically" because there's no signal weighting by trade value.

### TASK_713: Return-Weighted Trade Loss — DONE

Added return-magnitude weighting to per-asset policy loss:
- `return_boost = 1 + trade_strength * min(|asset_return| / mean_|return|, 10x)`
- High-value trades (asset earns ±2%) get up to 10x more gradient than near-zero trades
- Holds unaffected (boost = 1.0)
- Stacks on top of TASK_149 adaptive trade/hold balancing

Changes:
- `easy_trainer.py`: return-weighted loss after TASK_149 balancing
- `train_easy.py`: stores `per_asset_returns` in episode data, passes through to batch
- Fully checkpoint compatible, gracefully absent if key missing
