### AR Speed Is The Bottleneck

The fundamental cost problem:
- **0% AR**: ~90s/epoch (~1500 steps/s)
- **89% AR**: ~509s/epoch (~260 steps/s) — **5.7x slowdown**
- AR rollout = 336 sequential model forward passes per episode via `jax.lax.scan`
- 83% of epoch time is AR rollout, only 17% is actual gradient compute
- Each 1% AR increase adds ~5-6s/epoch

**AR is necessary** — without it, model trains on oracle state but at inference must use its own state → distribution mismatch → turtle (0% trades). But AR doesn't fix the real problem (distribution shift from synthetic → real data).

**Historical data won't help speed** — prices are just a different `(T, 64)` matrix, AR rollout cost is identical regardless of data source.

### AR Rollout Research Prompt

Created `prompt-lib/ar_rollout_speedup_research.md` — comprehensive research prompt for finding the best AR rollout optimization strategy.

10 concrete approaches explored:
1. **Batched episode rollout** — stack multiple AR episodes into one scan call
2. **Chunked rollout (K=8-16)** — freeze state within chunks, parallel forward passes
3. **Sparse rollout** — compute every M steps, interpolate between
4. **Reduced refinement** — fewer TRM cycles (H=2,L=4 vs H=6,L=8) for rollout only
5. **Distilled rollout model** — tiny 5M model for state generation
6. **Asynchronous rollout** — decouple from training loop
7. **Cached delta** — only recompute where actions changed
8. **Reduced precision** — bfloat16 for rollout
9. **XLA compilation analysis** — check scan efficiency
10. **Hybrid combinations** — theoretical 60-120x speedup

Plus 4 "nuclear options": remove state channels, learned state embedding, offline rollout, noisy oracle state.

Prompt structured for deep research (open-ended) though formatted more like a coding prompt. Core problem description and constraints are solid either way.

### AR Rollout Speedup Research (TASK_699) — 3 Model Consensus

Ran the AR rollout research prompt through Kimi K2, Gemini 2.5 Pro, and Claude (Opus deep research).

**Unanimous agreement**: Batched episode rollout (vmap B=6) is #1 priority — zero quality risk, 3-5x speedup from better GPU utilization. bf16 rollout inference is trivial add-on (+1.2-1.5x) but state accumulation MUST stay fp32.

**Claude's radical reframe**: Don't optimize the scan — eliminate it. 4/5 state channels (position, PnL, hold_duration, heat) are deterministic arithmetic computable via `jnp.cumsum`. Under teacher forcing with oracle actions, rollout cost → ~0 (100-1000x on rollout stage). Risk is exposure bias (training on oracle state, inference on model state), mitigated by scheduled sampling from seq2seq literature.

**Key disagreements**:
- Reduced TRM refinement: Gemini aggressive (H=2,L=2 = 12x FLOP cut), Claude conservative (L=4 = 2x), Kimi didn't explore
- Async pipeline: Gemini says 5.7x latency hiding, Claude says impossible on single GPU (JAX = one CUDA stream)
- Sparse/conditional rollout: Gemini and Claude both reject (`jnp.where` executes both branches, `lax.cond` breaks batching)

**Implementation order**: batch vmap → bf16 → scan tuning → evaluate → A/B test analytical states → reduced refinement → chunked (last resort)
