## Root Cause Analysis: Over-Trading

Detailed analysis of training metrics revealed the actual bottleneck:

| Epoch | agree_trade | agree_hold | Model Trade Rate | Over-trading |
|-------|-------------|------------|-----------------|-------------|
| 0 | 14.1% | 78.5% | 21.8% | 5.6× |
| 250 | 47.3% | 73.5% | 27.5% | 7.1× |
| 500 | 48.5% | 73.1% | 27.7% | 7.1× |
| 671 | 48.9% | 73.2% | 27.7% | 7.1× |

**The model is trapped in a precision-recall tradeoff:**
- As it learns to catch trades better (agree_trade 14%→49%), it simultaneously **degrades hold accuracy** (agree_hold 79%→73%)
- Net effect: balanced accuracy = 0.5 × trade + 0.5 × hold plateaus because trade↑ and hold↓ cancel exactly
- Oracle trades 3.9% of decisions; model trades **27.7%** — 7.1× over-trading
- The 25× adaptive trade weight in the loss creates a "when in doubt, predict trade" bias
- **This is the fundamental bottleneck, not model capacity or encoder width**

## TASK_689: Agent State Channels

### Concept

The model is blind to its own state — it doesn't know what positions it holds, how recently it traded, or whether positions are profitable. Adding agent state as extra input channels gives the model self-awareness to self-regulate trading frequency.

### Design (v3 — after 5 independent reviews)

**7 new channels** (observation: 27→34):

| Channel | Name | Type | What it tells the model |
|---------|------|------|------------------------|
| 27 | position_state | per-asset | Am I short (-1), flat (0), or long (+1)? |
| 28 | unrealized_pnl | per-asset | Am I winning or losing on this position? |
| 29 | hold_duration | per-asset | How long since I last traded this asset? |
| 30 | heat_fast | per-asset | Did I just trade this? (decay=0.80, ~3 steps) |
| 31 | heat_slow | per-asset | Is this a frequently-traded asset? (decay=0.99, ~70 steps) |
| 32 | capacity_usage | global | How many of my k=4 position slots are used? |
| 33 | confidence | per-asset | How confident am I in this prediction? |

### Key Design Decisions

1. **Oracle-independent**: State corruption during training (not teacher forcing) so model handles imperfect state at inference
2. **Position from oracle's `target_position`**: Not derived from action type (BUY/SELL are ambiguous — "close long" is SELL but results in flat, not short)
3. **Corruption over scheduled sampling**: Progressive noise injection is 99% cheaper than model-forward passes (400 per episode)
4. **Tiled, not evolved**: Current state only, broadcast across window — avoids causal leakage
5. **Multi-scale heat**: 2 timescales (fast=0.80, slow=0.99) — model learns which matters
6. **No phantom data**: Rejected cash/margin channels (don't exist in Easy Mode)

### Review Sources
- mem-001 (Opus): Bug fixes, lax.scan, confidence channel
- mem-002 (Opus): Critical position bug (BUY/SELL close vs open), corruption > scheduled sampling
- Sonnet: Tile not evolve, causal leakage concern
- Gemini: Global capacity channel, 2 heat > 3 heat, simulation vs reconstruction
- Fresh improvements: State corruption/denoising, multi-scale heat
- Gemini (final assessment): 9.8/10, ready for implementation

## Phase B Design Discussion

Three approaches considered for bridging train→inference gap:

### 1. Post-hoc state corruption (original spec)
- Flip positions, add PnL noise, heat noise, 5% full dropout
- **Problem**: creates impossible states (e.g., position flipped but PnL unchanged)
- Cheap and simple but unrealistic

### 2. Oracle entropy (preferred)
- Add noise to oracle *before* state channels are computed
- Random trade drops (oracle says trade → force hold, prob p)
- Random phantom trades (oracle says hold → force trade, prob q)
- State channels stay **internally consistent** — PnL, heat, duration all match noisy path
- ~5 lines of code change in `compute_target_position()` area
- **Best simulates actual inference failure mode** (model misses trades → wrong positions)

### 3. Dual dojo merging (after GPU install)
- Two branches, different seeds/batch sizes, merge checkpoints
- batch=512 on 3090 (exploitation) + batch=128 on CMP 90HX (exploration/noise)
- Natural corruption: merged model doesn't perfectly match either branch's oracle
- **Batch size asymmetry is a feature** — noisy 128 branch adds regularization
- Weight merging works fine across batch sizes (params are same shape)
- Needs CMP 90HX installed first (TASK_688)

### Decision: ~~Oracle entropy first, dual dojo after hardware~~ → Dual dojo implemented, hardware ready

### ~~Synergy~~ → CRITICAL BUG: State Channel Temporal Leak

98.5% agreement at epoch 431 was **too good**. Root cause: **state channels at time `t` leak the oracle's action at time `t`**.

**The leak:** `state_channels[start_idx:end_idx]` and `confidence[start_idx:end_idx]` use the SAME timestep as `policy_targets[start_idx:end_idx]`. The model sees the oracle's decision as input and is asked to predict it as output.

| Channel | What it encodes at time `t` | Leak severity |
|---------|---------------------------|---------------|
| position_state | Oracle position AFTER action at `t` | **CRITICAL** — directly IS the answer |
| unrealized_pnl | PnL from oracle position at `t` | **HIGH** — reveals position direction |
| hold_duration | 0 if oracle traded at `t` | **HIGH** — binary trade/hold signal |
| heat_fast | Spike if oracle traded at `t` | **HIGH** — trade signal |
| heat_slow | Slight bump if oracle traded at `t` | Mild |
| capacity | Positions including `t`'s action | **HIGH** — trade count signal |
| confidence | `max(oracle_softmax[t])` | **CRITICAL** — oracle certainty about target action |

**Fix:** Use `t-1` state (state BEFORE current decision):
```python
# BEFORE (leaked):
state_at_windows = state_channels[start_idx:end_idx]
conf_at_windows = confidence[start_idx:end_idx]

# AFTER (fixed):
state_at_windows = state_channels[start_idx - 1:end_idx - 1]
conf_at_windows = confidence[start_idx - 1:end_idx - 1]
```

Fixed in both `_generate_episode_data` and `_generate_batch_episodes` in `train_easy.py`.

**Implication:** ALL training from state_v1 onward was contaminated. The 72.7% synthetic and 68.4% Bella results from earlier runs were also inflated (just less obviously because training hadn't converged yet).

**Last honest checkpoint:** `state_v1_bella/phase1_epoch394.pkl` is NOT honest — it trained with the leak from the start. However, market channel weights (ch 0-26) are still valid; only state channel weights (ch 27-33) were trained on leaked signal.

After leak fix, dual dojo resumed from epoch 394 and recovered quickly:

| Epoch | Branch A Val | Branch B Val | Notes |
|-------|-------------|-------------|-------|
| 395 | 50.85% | 49.60% | Immediate drop (leak fixed) |

| 406 | — | 88.59% | Fast climb |
| 411 | 89.90% | 89.46% | Plateauing ~90% |
| 413 | 90.01% | — | New best |

**90% balanced accuracy is NOT a leak** — the `t-1` fix is verified (98.5% → 50% drop). But it IS inflated by oracle-quality state inputs:

- `position[t-1]`: oracle's position is perfectly consistent → trivially predicts "hold what oracle holds"
- `unrealized_pnl[t-1]` + `hold_duration[t-1]`: together predict when oracle will exit
- Oracle holds are ~96% of actions → knowing oracle's prior state narrows most predictions to "hold"

**The problem**: at inference, state comes from the MODEL's own (noisy) actions, not oracle's. First wrong prediction → wrong position → wrong PnL → cascading errors. The 90% training metric won't transfer.

**This is exactly what Phase B (oracle entropy) is designed to fix.** → See TASK_691.
