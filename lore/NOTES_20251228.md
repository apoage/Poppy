# Training Session Notes - December 28, 2025

## Major Fix: Negative Bias Bug in Reward System

### Problem Discovered
**Reward clipping at `[-10, 10]` was destroying positive information asymmetrically.**

Investigation revealed:
- 11 positive returns ≥10% were clipped to +10
- Only 6 negative returns ≤-10% were clipped to -10
- This created **systematic negative bias** in MC returns
- Loss was extremely high (1047+) and value head stuck at negative values (-33 to -58)
- Model couldn't learn positive rewards even on exploitable sine wave data

**Evidence from debug session:**
```
Sum of rewards: -148.26
Sum of actual % returns: -10.15
Clipped to +10: 1 time (but actual returns >= 10: 11 times!)
Clipped to -10: 7 times (actual returns <= -10: 6 times)
```

The clipping was destroying ~25 units of positive information vs ~17 units of negative information.

---

## Fix Applied: Symlog Reward Transformation

### 1. Replaced Clipping with Symlog (`vectorbt_env.py`)

**New function added (lines 41-67):**
```python
def symlog(x: np.ndarray, threshold: float = 1.0) -> np.ndarray:
    """
    Symmetric logarithmic transformation.
    - Linear near zero (|x| < threshold)
    - Logarithmic for large values
    - Perfectly symmetric: symlog(-x) = -symlog(x)
    """
    return np.sign(x) * np.log1p(np.abs(x) / threshold) * threshold
```

**Reward calculation updated (lines 928-936):**
```python
# OLD (BROKEN):
reward = np.clip(reward, -10, 10)

# NEW (FIXED):
reward = symlog(pct_return, threshold=1.0)
```

**Symlog Properties:**
| Input | Clipped | Symlog |
|-------|---------|--------|
| -100% | -10.0 | -4.615 |
| -50% | -10.0 | -3.932 |
| -20% | -10.0 | -3.045 |
| -10% | -10.0 | -2.398 |
| 0% | 0.0 | 0.000 |
| +10% | +10.0 | +2.398 |
| +20% | +10.0 | +3.045 |
| +50% | +10.0 | +3.932 |
| +100% | +10.0 | +4.615 |

**Key: Symlog preserves symmetry perfectly!**

## Critical Fix #2: Replay Buffer Sampling Bug

### Problem Discovered
**Replay buffer was sampling OLD/OVERWRITTEN data after wrap-around.**

Evidence from training:
- Model predicts: -98 (Value Head Peak bin=326/751)
- Batch targets mean: -10 to -11
- MC Targets mean: -0.19 to -0.28

The mismatch indicated the training data pipeline was broken.

### Root Cause Analysis

**Old sampling logic (BROKEN):**
```python
num_valid_trajs = min(self.num_trajectories, self.capacity)  # e.g., 5000
min_traj_idx = num_valid_trajs - safe_traj_count  # e.g., 2500
traj_indices = jax.random.randint(..., min_traj_idx, num_valid_trajs)  # [2500, 5000)
# ...
start_pos = self.trajectory_starts[traj_indices]  # Direct index lookup!
```

**The Bug:**
When `num_trajectories=6000` and `capacity=5000`:
1. New trajectories are written at `num_trajectories % capacity = 6000 % 5000 = 1000`
2. Most recent data is at physical indices [0, 1000)
3. But sampling was from [2500, 5000) - which contains OLD/OVERWRITTEN data!

### The Fix

**New sampling logic (CORRECT):**
```python
# Sample from LOGICAL indices [num_trajectories - N, num_trajectories)
safe_window = max(2, self.capacity // 500)  # ~10 for typical setup
start_logical = max(0, num_trajectories - safe_window)
end_logical = num_trajectories

logical_traj_indices = jax.random.randint(..., start_logical, end_logical)

# Map to PHYSICAL index in metadata array
physical_traj_idx = logical_idx % self.capacity
start_pos = self.trajectory_starts[physical_traj_idx]
```

### Verification

**Test 1: Small buffer (capacity=100, 20 trajectories)**
```
Buffer wraps: 2x
Expected: Recent trajectories 18-19 (rewards 180-190)
Actual sampled rewards: [180.0, 190.0]
SUCCESS!
```

**Test 2: Realistic buffer (capacity=5000, 25 x 500-step trajectories)**
```
Buffer wraps: 2.5x
Expected: Recent trajectories 15-24 (rewards 150-240)
Actual sampled rewards: [150.0, 160.0, ..., 240.0]
SUCCESS!
```

### Code Changed

**`mcts_trader/jax_agent/replay_buffer.py`** - `sample_batch()` method (lines 141-210):
- Sample from LOGICAL trajectory indices `[num_trajectories - safe_window, num_trajectories)`
- Map to PHYSICAL indices: `physical_idx = logical_idx % capacity`
- Added detailed comments explaining the fix

### Impact
This bug caused the model to train on stale/corrupted data, explaining why:
- Value predictions were disconnected from actual rewards
- Loss remained high even with correct reward scaling
- MC targets showed different distribution than batch targets

## Feature: Adaptive Entropy

### Problem
After ~400 epochs, policy collapsed to 95%+ HOLD. Entropy at 2.5-3.0 wasn't enough to force exploration. Model found +6% positive epochs occasionally but couldn't consistently replicate.

### Solution
Added adaptive entropy that boosts exploration when HOLD% exceeds threshold.

**CLI Arguments:**
```bash
python train_jax_fast.py --adaptive-entropy \
    --entropy-hold-threshold 0.70 \
    --entropy-boost-low 0.15 \
    --entropy-boost-high 0.30
```

**Behavior:**
| HOLD % | Entropy Coef |
|--------|--------------|
| < 70% | 0.01 (normal) |
| 70-80% | 0.15 (moderate) |
| > 80% | 0.30 (aggressive) |

**Output when triggered:**
```
[ADAPTIVE ENTROPY] HOLD=85.2% -> entropy_coef: 0.010 -> 0.300
```

### Code Changed
**`train_jax_fast.py`**:
- Added CLI args (lines 193-200): `--adaptive-entropy`, `--entropy-hold-threshold`, `--entropy-boost-low`, `--entropy-boost-high`
- Added adaptive logic in training loop (lines 559-574): checks hold_ratio after each epoch, adjusts `trainer.entropy_coef`

### Design Rationale
- **Self-regulating**: Only boosts when needed
- **Configurable**: All thresholds adjustable via CLI
- **Off by default**: Won't affect existing training runs
- **Gradual**: Two-tier boost (moderate then aggressive)
