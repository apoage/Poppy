### The four surprises that mattered

**Surprise 1 — TASK_697's pseudocode wasn't JIT-compatible.** The original §A.1 mapping table used Python `for` loops over `oracle_passes` and `visit_counts.at[idx].add(1)` writes. That works in NumPy; it does not work under `jax.jit`. The Phase-1 helper rewrote the math with vectorized argmax → one_hot → sum:

```python
per_pass_actions = jnp.argmax(all_policies.reshape(n_passes, T, n_assets, n_actions_per_asset), axis=-1)
visit_one_hot    = jax.nn.one_hot(per_pass_actions, n_actions_per_asset)
step_visit_counts = jnp.sum(visit_one_hot, axis=0)
step_policies    = step_visit_counts / n_passes
```

The operator joke from the build comment thread: *"not every time everything is written in vectors."* This is the documented lesson and deserves to be cited in the build cost. Most published ML pseudocode is Python-loops-over-things — the work of turning it into JIT-compatible JAX is non-trivial and easy to under-estimate. It rounded a Phase-1 deliverable that *looked* like "paste from spec" into a real implementation surface.

**Surprise 2 — Multipass Q-values are degenerate.** TASK_697 §A.1 row 4 mapped "per-pass returns ↔ backed-up leaf values". The Phase-1 agent discovered that in the simple multipass case, **all passes share the same `clean_pnl[T-1]`** — passes differ in *which assets they select* under noise perturbation, not in *which realized return they observe*. The clean path provides the value-target trajectory per `path_solver.py:270-279`; per-pass noise affects selections, not returns. This collapses per-slot Q-values to `total_pnl * visit_indicator` — the trivial degenerate case TASK_697 flagged as "Open Question 1". The Phase-1 helper computes and exposes `q_values` for diagnostic use but `oracle_distill_q_value_weight` defaults to **0.0** in the config. A Phase-6 upgrade would compute per-pass actual realized PnL along each pass's selected path; that is not on the ship gate.

**Surprise 3 — Phase 2 didn't need any train_phase2 branch.** The Phase-2 dispatch flagged "latent_std parity" as the hardest unknown ahead of Phase 3. The expectation was that bridge-trained dynamics weights would diverge from canon He-normal init enough to break Stage-A's bootstrap. The Phase-3 integration smoke ran the bridge ckpt through `train_phase2.load_phase1_checkpoint(...)` and the **6 gates passed clean**:
- gate (i): `load_phase1_checkpoint` accepts bridge ckpt — PASS.
- gate (ii): bridge dynamics NOT all-zero (warm from Phase-A) — PASS.
- gate (iii): `initialize_missing_aux_heads` leaves dynamics untouched — PASS (`initialize_dynamics` is *idempotent*; it only fills tensors that are all-zero).
- gate (iv): bridge `consistency_loss` ≤ 2× cold-start canon — PASS (2.08 vs 2.05).
- gate (v): **latent_std parity ratio 0.95** within the 50% margin — PASS.
- gate (vi): `--encoder-lr` + `--encoder-unfreeze-epoch` parse correctly — PASS.

Zero `train_phase2.py` body changes required. The existing aux-head init machinery is more permissive than the spec assumed. The Phase-3 agent's deliverable was tooling, not surgery.

**Surprise 4 — Joint argmax over 320 slots for unroll actions.** `recurrent_inference` takes a single `(batch,)` int action per step (`muzero_model.py:701-728`), but the multipass oracle's per-step action target is `(T, n_assets)` — 64 per-asset actions per step. The Phase-2 contract chose joint argmax over the flat 320-slot policy distribution for the dynamics unroll, leaving the per-asset target intact for the policy CE. A Phase-6 upgrade would extend the dynamics block to consume per-asset action embeddings (a model-tree change); this is parked.
