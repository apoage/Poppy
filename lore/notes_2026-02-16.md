## TASK_673: Multipass Oracle — Degradation Diagnosed

Training with multipass oracle (launched overnight) showed regression: **51-52% agreement vs 56% baseline** after 650 epochs and 70 merges. Not recovering.

### Root Causes

**1. Noisy value targets (critical)**: `avg_cumulative_pnl` was averaged across 10 noisy oracle passes. Each pass trades different assets at different times on noisy returns → averaged PnL curve is a blurred fiction. Value head trained on unrealizable PnL → pollutes shared model trunk.

**2. noise_scale=0.1 too aggressive**: With `min_alpha_threshold=0.001` and return std ~0.02, noise std = 0.002 — **2x the threshold**. Marginal trade signals (the ones that matter most for balanced accuracy) get randomly flipped.

### Fixes Applied

**Fix 1: Clean oracle PnL for value head** (`path_solver.py`)
- `multipass_oracle_policy` now runs a clean (no-noise) `greedy_lookahead_path` first
- Returns `clean_path.cumulative_pnl` instead of averaged noisy PnL
- Policy targets still come from multipass (soft), value targets from clean oracle (exact)
- Verified: `jnp.allclose(mp_pnl, clean_pnl) = True`

**Fix 2: Reduced noise_scale 0.1 → 0.03** (`easy_config.py`)
- 3% of return std instead of 10%
- Noise std ≈ 0.0006 vs threshold 0.001 (below threshold, not above)
- Soft targets at noise=0.03: 0.5% of timesteps (very conservative)
- Only the most ambiguous decisions get softened

### Status

Code patched but **training still running old code**. Needs restart to pick up fix.

## TASK_674: Agreement Plateau — Deep Review & Bug Fixes

Deep code review of the 52-53% agreement plateau. Found 6 bugs, applied all code fixes.

### Bugs Fixed

| Bug | Severity | File | Fix |
|-----|----------|------|-----|
| Buffer sample counter `+= 1` instead of `+= take_count` | CRITICAL | `train_easy.py:635` | Buffer now refreshes 17× more often — model sees 17× more unique data |
| Optimizer warmup reset on every merge | HIGH | `easy_trainer.py:457-466` | Preserve adam + schedule counts across merges. Removes 15-20% training waste |
| Damaged checkpoint from broken multipass run | — | Runtime | Needs `reset_edojo.sh` before fresh start |
| Train/val use same generator (data leakage) | MEDIUM | `train_easy.py:979-1001` | Separate `val_generator` with seed offset +7919 |
| Value support under-utilization (15% of bins) | LOW | `easy_config.py:43` | `value_scale` 1.0 → 2.0 (30% bins, safe for PnL ≤ 5) |
| Zero-return maps to SHORT in oracle | LOW | `path_solver.py:725` | Three-way where: long/short/flat |

### Review findings — NOT bugs (investigated & rejected)

- Adam bias correction after zeroing mu: 44-step soft warm-in, not a permanent collapse. Much better than 1000-step hard warmup.
- Soft-target weighting threshold at 0.5: multipass targets are highly peaked (>95%), threshold works fine.
- State-value information gap: position-dependent component ~0.1% at current transaction costs. Negligible.
- Multipass oracle real vs noisy returns: intentional — noise varies selection, real returns determine direction.
- Empty selection PnL: correctly handles closing costs when no assets selected.
- e-dojo merge interval reset: recomputed from epoch deltas each poll, not accumulated.

### Key insight: Bug 1 was the plateau root cause

With `+= 1`, each episode was sampled 3400 times before refresh (17× oversampled). The buffer of 16 episodes cycled every ~213 batches. The model was training on the same 16 episodes over and over — neither memorizing (too much noise) nor generalizing (too little variety). This explains why both train AND val were stuck at ~50%.

## Gradient Drowning: Agreement Stuck at 50%

After 35 epochs with all TASK_674 + TASK_675 fixes, agreement remained flat at 50.00% — the model was producing all-HOLD (the "turtle" strategy). Loss was *increasing* (2.72 → 2.88) as trade weight warmup ramped up but couldn't overcome hold dominance.

### Root Cause: Two Bugs in Adaptive Trade Weighting

**Bug 1: `MAX_TRADE_WEIGHT = 10.0` too low**

With ~63 holds and ~1 trade per batch (63:1 ratio), the ideal trade weight is 63.0. But `MAX_TRADE_WEIGHT = 10.0` capped it there, leaving **6.3× hold gradient dominance**. The model learned "always HOLD" because hold gradients overwhelmed trade gradients.

**Bug 2: Binary `is_trade` mask discarded soft targets**

```python
# OLD (broken): binary threshold on soft multipass probabilities
is_trade = targets_reshaped[:, :, 1] < 0.5  # 0 or 1
loss_weights = jnp.where(is_trade, adaptive_trade_weight, 1.0)  # step function
```

With multipass oracle, targets are soft (e.g. 60% HOLD, 40% BUY). A target with `hold_prob=0.6` is **not a trade** under the binary mask (0.6 > 0.5), so it gets weight 1.0 instead of the adaptive weight. Near-trade signals — the most informative ones — got zero boosting.

### Fixes Applied (`easy_trainer.py`)

```python
# NEW: continuous trade strength from soft targets
hold_prob = targets_reshaped[:, :, 1]     # (batch, 64) continuous [0, 1]
trade_strength = 1.0 - hold_prob          # 0.0 = hold, 1.0 = trade

n_trades = jnp.maximum(jnp.sum(trade_strength), 1.0)
n_holds = jnp.maximum(jnp.sum(hold_prob), 1.0)

MAX_TRADE_WEIGHT = 64.0   # Was 10.0 — now allows full gradient balance
target_trade_weight = jnp.minimum(n_holds / n_trades, MAX_TRADE_WEIGHT)

# Continuous blending instead of step function
loss_weights = 1.0 + trade_strength * (adaptive_trade_weight - 1.0)
policy_loss = jnp.sum(per_asset_ce * loss_weights) / jnp.sum(loss_weights)
```

**Result**: Trade gradients now have equal mass to hold gradients. Soft multipass targets contribute proportionally.

### Why This Matters

Without this fix, the model is trapped: hold gradient mass always dominates, so "always HOLD" is the local minimum. Even with perfect data (TASK_674 buffer fix), correct LR schedule (TASK_675), and clean oracle targets (TASK_673), the gradient signal for trades was being drowned. This was the final piece — the model couldn't learn to trade because it was never given a fair gradient signal to do so.

## TASK_677: Turtle Breaker — Warmup Was the Final Piece

### LR=0.1 Experiment (proof that warmup is the problem)

Ran with `--lr 0.1` (333× default) to test if the turtle was a local-minimum issue:
- **Epoch 0**: Loss 3.98 → 8.0 → 2.7 (wild oscillation), agreement 50.00%
- **Epoch 1**: Loss **explodes to 331.8** (massive overshoot), recovers to 3.6, agreement still 50%

The model oscillates violently but **still turtles**. This proves the problem is gradient *direction*, not magnitude. A bigger LR just moves toward turtle faster.

### Root Cause: `weight_warmup_epochs = 50`

Even with continuous trade_strength and MAX_TRADE_WEIGHT=64 (the gradient drowning fix), the warmup nullifies it:
```
epoch 0:  warmup_progress = 0/50 = 0.0  → adaptive_trade_weight = 1.0  (NO boost)
epoch 25: warmup_progress = 0.5         → adaptive_trade_weight = 32.0 (half boost)
epoch 50: warmup_progress = 1.0         → adaptive_trade_weight = 63.0 (full boost)
```

For 50 epochs, the 63 holds drown the 1 trade. The model entrenches turtle before trades ever get a voice.

### Fix Applied

`easy_config.py`: `weight_warmup_epochs: 50 → 0`

From step 1: adaptive_trade_weight = 63.0, trade gradient mass = hold gradient mass. No ramp, no turtle window.

## Multi-GPU Training Discussion

Explored feasibility of 4-GPU parallel training:

### Approaches Discussed

1. **Data Parallelism** (`jax.pmap`): Split batch across GPUs, sync gradients via `lax.pmean`. Linear speedup, simple. Requires identical model copies.
2. **Population-Based Training (PBT)**: Independent agents with periodic weight sharing. More diverse, tolerates different hyperparams. AlphaStar-style league training.
3. **E-dojo Multi-Branch**: Extend current dual-branch to 4-branch with tournament-style merging.

### AlphaStar League Training

Key insight from the discussion: AlphaStar is basically a mortal model tournament — agents trained against each other with different strategies, best performers contribute to the main agent. Applicable to trading: different agents could specialize in different market regimes, with periodic tournaments to select and merge the best.

Not implementing now — single-GPU training needs to work first.
