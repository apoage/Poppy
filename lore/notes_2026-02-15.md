## TASK_673: Multipass Oracle (REVIEWED)

Training plateau at ~56% agreement. Root cause: binary oracle with k=1 sees only one valid path, but often 5-10 assets have similar expected returns. Model is punished for picking asset 12 instead of asset 7, even when both are equally profitable. The model needs to learn "find a profitable path" not "replicate this exact path."

### Corrected Approach: Average Policies, Not Selections

Original plan averaged binary *selections* then passed through `optimal_path_to_policy` — broken because `jnp.where` binarizes any non-zero value (0.15 gets same logits as 1.0).

**Fixed algorithm**:
1. Run oracle N times with Gaussian noise on returns → N different binary paths
2. Convert each binary path → one-hot policy via existing state-aware logic (TASK_141)
3. Average the N one-hot policies → genuinely soft distribution

```
10 passes with noise:
- 6 say BUY asset 7    → one-hot BUY for asset 7
- 3 say BUY asset 12   → one-hot BUY for asset 12
- 1 says HOLD all      → one-hot HOLD everywhere
Average: Asset 7 BUY=0.6, Asset 12 BUY=0.3, HOLD~0.1
```

**Key**: Each pass produces correct one-hot targets through existing state-aware logic. The softness comes from *averaging after* conversion, not from hacking `optimal_path_to_policy`.

### Implementation: `multipass_oracle_policy()` in path_solver.py

- Single function does oracle + policy conversion (no separate `OptimalPath`)
- Returns `(soft_policy, avg_cumulative_pnl, avg_total_alpha)` directly
- Inner `vmap` over n_passes, outer `vmap` over N episodes in batch
- 3 config fields in `easy_config.py`: `oracle_multipass`, `oracle_n_passes`, `oracle_noise_scale`
- `if getattr(config, 'oracle_multipass', False)` gate in both code paths of `train_easy.py`

### Downstream: Zero Changes Needed

- Loss: `softmax_cross_entropy(logits, soft_target)` = KL divergence + constant
- TASK_149 adaptive weighting: `< 0.5` threshold on HOLD prob works with soft targets
- Agreement metric: `argmax(soft_target)` = consensus action, still correct
- Value head: averaged `remaining_pnl` = expected future value under ensemble

Full details: `tasks/TASK_673_MULTIPASS_ORACLE.md`

## TASK_673: Literature Review

Deep research on the multipass oracle approach. Key finding: **strongly validated by literature across 8 papers, no implementation changes needed.**

### Directly Analogous: Soft-Label Imitation Learning (Hassouna et al., 2025)

**"Learning Topology Actions for Power Grid Control: A Graph-Based Soft-Label Imitation Learning Approach"** — https://arxiv.org/abs/2503.15190

Exact same pattern as TASK_673:
- **Problem**: Multiple valid actions per state (like multiple valid assets to trade)
- **Method**: Simulate N different actions, score each by effectiveness, build soft probability distribution
- **Result**: **+17% over the hard-label expert** — student surpassed the teacher
- Their domain (power grid topology) has the same structure: combinatorial action space, multiple near-optimal choices, hard oracle picks one arbitrarily

This is the strongest validation for TASK_673.

### Theoretical Foundation: Why Soft Targets Work

**Hinton et al. 2015** — "Distilling the Knowledge in a Neural Network" (https://arxiv.org/pdf/1503.02531)
- Soft targets from ensembles transfer generalization ability
- High-entropy targets provide more information per training sample than hard targets

**ICLR 2025** — "Towards Understanding Why Label Smoothing Helps" (https://proceedings.iclr.cc/paper_files/paper/2025/file/9dc5accb1e4f4a9798eae145f2e4869b-Paper-Conference.pdf)
- Theoretical proof: soft targets → **lower conditioning number** → faster convergence
- Soft targets promote **neural collapse** (features align to simplex) more strongly
- Smoother loss landscape → more stable training

### The Mode Averaging Catastrophe (Why Our Approach Is Safe)

**Behavior Transformers (BeT)** — NeurIPS 2022 (https://arxiv.org/abs/2206.11251)
**Diffusion Policy** — Chi et al. 2023 (https://arxiv.org/abs/2303.04137)

When demonstrations contain multiple valid strategies (go left OR right), averaging *actions* collapses them into invalid middle (go straight into wall). Our approach avoids this because we average *probability distributions*, not actions. If 6/10 passes say BUY asset 7 and 4/10 say BUY asset 12, the averaged policy preserves both modes: "60% asset 7, 40% asset 12." Equivalent to a mixture model.

### DART: Noise Injection for Robust IL (Laskey et al., 2017)

https://arxiv.org/abs/1703.09327

- Injects calibrated Gaussian noise into expert's actions during demonstration
- Creates "funnel of corrective examples" around expert trajectory
- **+62% over vanilla behavioral cloning** on real robot tasks
- Noise level should match expected model error magnitude

Our `noise_scale=0.1` (10% of return std) is analogous. Difference: DART perturbs actions, we perturb observations (returns). Same effect — exploring the neighborhood of the optimal policy. DART's adaptive noise optimization is a potential future extension.

### Policy Distillation (Rusu et al., 2016)

https://arxiv.org/abs/1511.06295

- Training student on soft Q-value distributions (with temperature) from teacher
- 15x model compression without performance loss
- Soft targets encode "which alternative actions are almost as good"

### DAgger: Dataset Aggregation (Ross et al., 2011)

https://arxiv.org/abs/1011.0686

- Iteratively collects data under current policy, queries expert
- Addresses covariate shift (BC regret O(T^2 eps) → DAgger O(T eps))
- Complementary to multipass: we improve *quality of each query*, DAgger improves *when to query*

### Summary Table

| Concept | Paper | Key Result | TASK_673 Equivalent |
|---------|-------|------------|---------------------|
| Soft labels from multiple evaluations | Hassouna 2025 | +17% over hard-label expert | N noisy oracle passes → avg policies |
| Noise injection on oracle | DART 2017 | +62% over vanilla BC | Gaussian noise on returns |
| Soft targets improve convergence | ICLR 2025 | Lower conditioning, faster convergence | CE on soft targets = KL divergence |
| Avoid mode averaging | BeT 2022, Diffusion Policy 2023 | Don't average actions | Average *distributions* — modes preserved |
| Ensemble → student | Policy Distillation 2016 | 15x compression, no degradation | N oracle passes = ensemble of experts |
| Covariate shift correction | DAgger 2011 | O(T) vs O(T^2) regret | Complementary, future stacking |

### Impact on TASK_673: No Changes

The research validates TASK_673 strongly but doesn't require implementation changes:
- Architecture (avg policies not selections) is already correct
- `noise_scale=0.1` is in line with DART's recommendations
- Existing `softmax_cross_entropy` is the right loss for soft targets
- The only additions would be future extensions (adaptive noise, per-asset scaling)

## Yarrow: Vision Sketch + Naming Philosophy

Researched OpenClaw (formerly Clawdbot) and Claude Code Swarms (Agent Teams) to compare
against the Yarrow multi-agent architecture designed earlier.

### Comparison Summary

| | **Yarrow** | **OpenClaw** | **Claude Code Swarms** |
|---|-----------|-------------|----------------------|
| Purpose | Code review + generalizable | Life automation (email, calendar) | Code implementation |
| Agent model | Multi-provider ensemble (6 LLMs) | Single model per instance | Multiple Claude instances |
| Specialization | Hard role boundaries (enforced) | Persona files (not enforced) | Soft prompting |
| Inter-harvester comms | None (anti-groupthink) | Disabled by default | Direct messaging |
| Ensemble voting | Yes, precision-weighted | No | No |

Yarrow's architecture is structurally unique: diverse models forced into independence,
with precision tracking per agent. Not parallelism — structured disagreement.

### Generalized Architecture (yarrow/vision.md)

Realized the hierarchy isn't a code review tool — it's a **decision-quality pattern**
that generalizes to any domain:

```
Diverse perspectives → noise reduction → validated decision → precise execution
```

Same pipeline, different schemas per domain (code review, architecture design, research,
trading decisions). Wrote `yarrow/vision.md` as the design sketch.

### The Naming Insight

The apothecary metaphor isn't decoration — it IS the architecture. An apothecary works
with powerful, dangerous materials (belladonna heals eyes or kills, poppy stops pain
or stops breathing). The entire profession exists because these substances demand protocol:

- **Harvester** gathers the plant. Doesn't decide the dose.
- **Apprentice** grinds and sorts. Doesn't write the prescription.
- **Apothecary** reads symptoms, decides treatment. Doesn't touch the mortar.
- **Compounder** mixes exactly what's prescribed. Doesn't improvise.

Remove any boundary and someone dies. That's safety engineering, not bureaucracy.

LLMs are the dangerous materials — powerful, unpredictable, capable of brilliance or
hallucination. A swarm just throws them at the problem and hopes. An apothecary shop
handles them with the respect they require: every role constrained, every handoff
inspectable, trust earned by track record.

Yarrow itself — the wound-healing herb that stops bleeding. It doesn't cause action,
it **controls the response**. The whole project naming (Poppy, Bella, Foxglove, Yarrow)
follows the same worldview: plants that heal or kill depending on how carefully you
work with them. Not a theme — a philosophy.

### Architecture Summary

```
User (gear shift: plan/approval/yolo)
  └── The Apothecary (orchestrator, Claude Opus)

        │     └── findings/ ← 7 harvesters write here
```

### Key Design Decisions
- Each harvester has explicit "What You Are NOT Looking For" — prevents overlap
- Harvesters never see each other's findings (anti-groupthink)
- Apprentice handles deduplication (keeps orchestrator context clean)
- Orchestrator knows harvester deployment strategy (which to send per target type)
- All communication via filesystem (inspectable, git-trackable, crash-recoverable)
- Ensemble scoring weighted by per-agent precision (tracked over time)
