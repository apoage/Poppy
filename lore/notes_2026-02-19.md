## TASK_682: Real Data Benchmark — PLANNED

### Context

Training at 60%+ on synthetic/Bella but zero visibility into real market data performance.
TASK_666 spec requires "positive alpha on 4/6 benchmark periods" as Phase 1 success criteria.
The 6 benchmark periods in `config/benchmark_periods.json` have never been evaluated against.

### Plan Summary

Create `tools/benchmark_easy.py` — standalone benchmark tool that:
1. Loads real prices from DB for each benchmark period via `HistoricalMarket`
2. Runs oracle (`greedy_lookahead_path`, k=4) + model on those prices
3. Computes agreement, P&L, alpha, Sharpe, max drawdown per period
4. Prints formatted report + optional JSON output

Key design decisions:
- Reuse heavily from `benchmark_oracle_vs_model.py` (P&L simulation, model loading)
- `HistoricalMarket(n_assets=64)` auto-selects top 64 assets per period
- Model doesn't learn asset identity (synthetic data) — top-64 per period is fine
- Batch inference at 512 windows to avoid OOM on ~10k windows per period
- New `simulate_model_pnl_detailed()` wrapper for per-step returns (Sharpe computation)
- Add `--benchmark` flag to `train_easy.py` for post-training eval

Full plan written to `tasks/TASK_682_REAL_DATA_BENCHMARK.md` — sent for independent review.

### Benchmark Alignment Check

Identified gap: TASK_666 Phase 4 specified `run_easy_eval()` with P&L/alpha/Sharpe on benchmark periods, but this was never implemented. The existing `benchmark_oracle_vs_model.py` is designed for `train_jax_fast` (full pipeline), not easy mode. TASK_682 fills this gap.

## TASK_677: Oracle Sharpening — Implemented

Post-averaging temperature sharpening for multipass soft targets. When 10 oracle passes
produce 70% BUY / 30% HOLD, sharpening at temperature=0.1 converts to 99.99% BUY / 0.01% HOLD.
Genuine ambiguity (50/50) preserved. Already-peaked targets unchanged.

### Files Changed

| File | Change |
|------|--------|
| `easy_config.py:68` | Added `oracle_sharpen_temperature: float = 0.1` |
| `path_solver.py` | `sharpen_temperature` param + log→scale→softmax per-asset after multipass averaging |
| `train_easy.py` | Threads `oracle_sharpen_temperature` to both single and batched oracle calls |

### Context

Training at 60% with multipass active — soft targets are going in blurred. Sharpening
gives the model "commands" (sharp BUY) instead of "suggestions" (70/30 distribution).
Combined with k=4 (TASK_681) and v3 encoder (TASK_676), this is the last gradient clarity fix.

Active on next restart. Current run uses old code (no sharpening).

## TASK_682: Implementation — DONE

### Files Created/Modified

| File | Action | Purpose |
|------|--------|---------|
| `tools/benchmark_easy.py` | **NEW** | Core benchmark: load DB prices, run oracle+model eval, format report |
| `train_easy.py` | **MODIFIED** | Added `--benchmark` flag for post-training eval |
| `tasks/TASK_682_REAL_DATA_BENCHMARK.md` | **MODIFIED** | Status → IMPLEMENTED |

### Implementation Details

- Reuses heavily from `benchmark_oracle_vs_model.py` (P&L simulation, oracle conversion, metrics)
- Custom `create_model()` that respects `encoder_version` from checkpoint config (V2/V3)
- Batched encode+infer (128 windows/batch) to cap VRAM
- `_simulate_pnl_vectorized()` for faster random baseline (~5.5s vs 172s)
- Hold-biased random baseline (90/5/5, 20 trials)
- `max_len` parameter passed to `greedy_lookahead_path` for 10k+ step sequences
- Backward-fill for initial zero prices (assets with no data at period start)
- Value MSE computation (model value vs oracle cumulative P&L × value_scale)
- Full 6-period report with TASK_666 success criteria

### Bugs Fixed During Implementation

1. **OOM on oracle**: `greedy_lookahead_path` default `max_len=512` too small for 10k+ steps → pass `T_returns` directly
2. **Encoder version mismatch**: `create_model` from `benchmark_oracle_vs_model.py` didn't pass `encoder_version` → local version that does
3. **OOM on model inference**: 512-window batch too large → reduced to 128
4. **Zero prices at start**: HistoricalMarket forward-fill can't fix row 0 → added backward-fill
5. **Slow random baseline**: Python per-asset loop × 100 trials = 173s → vectorized + 20 trials = 5.5s
