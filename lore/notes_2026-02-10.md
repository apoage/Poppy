## TASK_142: Darwinian Orchestrator Fixes

### Problem Discovery
8 hours of dual-bella training (1260+ epochs) resulted in:
- **0 merges** executed
- Agreement stuck at ~1% (random chance)
- Cosine similarity crashed to 0.427

### Root Cause: Chicken-and-Egg Divergence Brake

The divergence brake was designed to restart the worse branch when cosine drops below 0.85. But:
1. Brake activates → tries to restart from merged checkpoint
2. No merged checkpoint exists (no merges ever happened!)
3. Returns None → no action taken
4. Branches keep diverging → brake keeps triggering → infinite loop

```
dojo_state.json showed:
  merge_count: 0
  steps_since_merge: 887600
  cosine: 0.427  ← critically diverged
```

### Additional Issues Found
1. **Cold Start Divergence**: Branch A started fresh (no checkpoint), Branch B from checkpoint
2. **Destructive Inversion**: `--invert-returns` flipped raw returns post-generation, breaking OHLC structure
3. **Basin Desync on Restart**: Each branch used its own checkpoint instead of syncing to same one

## Fixes Implemented

### Fix 1: Divergence Brake Fallback (Priority 1)
`e-dojo_v1.py` lines 520-530

When brake triggers but no merged checkpoint exists:
- Fall back to better-performing branch's checkpoint
- Use that to restart the worse branch
- Breaks the chicken-and-egg loop

### Fix 3: Basin Synchronization (Priority 3)
`e-dojo_v1.py` lines 812-848

When auto-resuming without merged checkpoint:
- Check BOTH branch directories for checkpoints
- Find the NEWEST checkpoint from ANY branch
- Use that SAME checkpoint for BOTH branches


### Previous Fix: Physics-Preserving Inversion
Changed from `--invert-returns` (post-hoc return flip) to `--invert-regime`:
- Swaps crash(0)↔rally(1) at Bella generation time
- Preserves OHLC structure (High > Low always true)
- Markets look realistic, just opposite direction

## Architecture: Darwinian Orchestrator

The e-dojo now implements survival-of-the-fittest:

```
┌─────────────────────────────────────────────────────────┐
│                    DARWINIAN DOJO                        │
├─────────────────────────────────────────────────────────┤
│  cos > 0.95:  FedAvg (blend equally)                    │
│  cos 0.90-0.95: TIES (resolve sign conflicts)           │
│  cos 0.85-0.90: Fisher normalized (importance weight)   │
│  cos < 0.85:  BRAKE → restart worse from better's ckpt  │
├─────────────────────────────────────────────────────────┤
│  Basin Sync: Both branches always start from SAME ckpt  │
│  Fallback Chain: merged → better_branch → fresh start   │
└─────────────────────────────────────────────────────────┘
```

The weaker branch doesn't drag down the stronger - it gets reset to catch up.

## TASK_145: Critical Architectural Fixes (THE BIG ONE)

### Bug 1: Softmax Competition (Policy Head)

**Problem**: Single 320-dim softmax forces all 64 assets to compete for probability.

```python
# BROKEN: Assets compete
policy_loss = softmax_cross_entropy(logits_320, targets_320)

# FIXED: Independent per-asset
logits_64x5 = logits.reshape(-1, 64, 5)
targets_64x5 = targets.reshape(-1, 64, 5)
policy_loss = softmax_cross_entropy(logits_64x5, targets_64x5).mean()
```

### Bug 2: Value Head Mismatch (Logic Bomb)

**Problem**: With `oracle_k=10`, value head learns 10-asset portfolio returns. Model executes 1 trade.

**Impact**: MCTS sees value=+2% but achieves +0.2% → tree collapse.

**Fix**: `oracle_k=1` - value head predicts realizable single-trade returns.

### Bug 3: Majority HOLD Gradient Washout

**Problem**: With k=1, oracle is 98.4% HOLD. Model learns "lazy holding" for 90%+ agreement.

**Fix**: Action-weighted loss. Trades weighted 5x:

```python
is_trade = targets[:, :, 1] < 0.5  # NOT HOLD
loss_weights = jnp.where(is_trade, 5.0, 1.0)
policy_loss = jnp.sum(ce * loss_weights) / jnp.sum(loss_weights)
```

### Final Configuration

```python

trade_loss_weight: float = 5.0         # Trades weighted 5x vs HOLD
target_oracle_agreement: float = 0.995 # 99.5% (was 85%)

```

## TASK_147: Agreement Metric Semantic Fix

### The Problem

Even after TASK_146 fixes, training showed 98.4% agreement from step 100. Model learned to output HOLD everywhere - matching the oracle's 98.4% HOLD rate with k=1.

**Root cause**: The metric measured 64 independent hold/trade decisions. With k=1:
- Oracle: BUY asset 7, HOLD the other 63
- Model: HOLD all 64
- Agreement: 63/64 = 98.4% ← WRONG!

The model wasn't learning the optimal path. It was learning to output background noise (HOLD) that matched the oracle's background.

### The Fix: Balanced Accuracy

Split agreement into trade vs hold, weight equally:

```python
# TASK_147: Balanced Accuracy
agree_trade = accuracy on oracle's TRADE signals only
agree_hold = accuracy on oracle's HOLD signals only
balanced_agreement = 0.5 * agree_trade + 0.5 * agree_hold
```

| Model Behavior | agree_trade | agree_hold | Balanced |
|----------------|-------------|------------|----------|
| Turtle (all HOLD) | 0% | 100% | **50%** |
| Random | ~20% | ~80% | **~50%** |
| Learning | ↑ | stable | **> 50%** |

### Changes Made

**easy_trainer.py**:
- `train_step`: Added `agree_trade`, `agree_hold`, `balanced_agreement` metrics
- `evaluate_batch`: Same balanced accuracy (fixed after first test showed Val still at 98.4%)
- `oracle_agreement` now uses `balanced_agreement` in BOTH functions

**easy_config.py**:
- `target_oracle_agreement: 0.75` (was 0.995, meaningless with old metric)

### Bug Caught in Testing

First run after TASK_147 showed:
```

Val Agree: 98.4%    ← WRONG (evaluate_batch still used old metric)
```

Fixed by updating `evaluate_batch` to also use balanced accuracy.

### Trade Weight Tuning (Post-Test)

After 29 epochs, model converged to perfect turtle:

## TASK_149: Adaptive Class Balancing

### Problem with Fixed Weight
TASK_147's fixed 60.0 weight assumes exactly 1.6% trades per batch. But:
- Some batches have more trades (easier episodes)
- Some batches have fewer trades (quiet markets)
- Different oracle_k values need different weights

### Solution: Dynamic Per-Batch Weighting
Instead of a fixed weight, calculate it per batch:
```python
n_trades = jnp.maximum(jnp.sum(is_trade), 1.0)
n_holds = jnp.maximum(jnp.sum(~is_trade), 1.0)
adaptive_trade_weight = n_holds / n_trades  # e.g., 63/1 = 63.0
```

### Benefits
- **Exact 50/50 balance**: Every batch gets perfect gradient balance
- **Auto-adjusts to oracle_k**: No manual tuning needed
- **Handles batch variance**: Different episodes, different trade densities

### Files Modified
- `easy_trainer.py:157-170`: Adaptive weight calculation
- `easy_config.py:44-46`: Deprecated fixed weight field

### New Metric
`adaptive_trade_weight` added to training metrics for monitoring

## TASK_148: Breaking Bootstrap Deadlock

### The Problem
Random weights start with cosine ~0.46 (below brake threshold 0.85). The old logic:
```python
if cosine < brake_threshold:
    if merge_count == 0:
        return False, "fresh_start_skip_brake"  # TRAP!
```

This skipped the interval check entirely, so no merge ever happened. No merge → no `merged_latest.pkl` → divergence brake can never activate → infinite loop.

### The Fix
Allow first merge even when diverged, as long as we've waited for the interval:
```python
if merge_count == 0:
    if steps >= interval:
        return True, "initial_sync_merge"  # Force baseline
    return False, "fresh_start_wait_for_interval"
```

## TASK_151: Signal Soft-Start (Warmup Phase)

### The Problem
TASK_149's adaptive weighting jumps to 50% trade gradient mass instantly. On fresh random weights, this can cause:
- Gradient explosion / NaNs
- Early weight fracturing
- Rapid branch divergence

### The Fix
Linear ramp over first 50 epochs:
```python
warmup_progress = min(epoch / warmup_epochs, 1.0)
active_weight = 1.0 + (target_weight - 1.0) * warmup_progress
```

| Epoch | Weight (if target=63) |
|-------|----------------------|
| 0 | 1.0 (unweighted) |
| 25 | 32.0 (halfway) |
| 50+ | 63.0 (full adaptive) |

## TASK_152: Untiling the Encoder (Final Boss)

### The Fix
