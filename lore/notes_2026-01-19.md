## TASK_064: Smart Environment Data Allocation

### The Problem

Started with what seemed simple: "load data smarter, save some DB reads."

Current parallel env setup had issues:
- All 15 envs loading same data (15× DB reads)
- Random sampling from anywhere in the period
- **Causality violation**: future data mixed with past
- Model seeing shuffled time, learning spurious correlations

### The Iceberg

Every "simple" fix revealed another constraint:

```
Surface: "Just load data smarter"

Below:
  ├─ Causality constraints (time must flow forward)
  ├─ i.i.d. requirements (batches need regime diversity)
  ├─ Forgetting dynamics (can't stay in one regime too long)
  ├─ Physics coherence (can't mix regimes within epoch)
  ├─ Memory limits (can't load everything at once)
  └─ Architecture rewrite (dojo isn't built for this)
```

### Key Insights from Planning

1. **Sequential/Local tiling violates i.i.d.**
   - Env 0 → day 0, Env 1 → day 1, etc.
   - Entire batch sees same market regime
   - Gradient whiplash when regime changes

2. **Epoch-isolated allocation causes forgetting**
   - Epochs 0-14 all on Period 1, then all on Period 2...
   - Model forgets Period 1 while training on Period 2

3. **Solution: Two-level allocation**
   - STRATIFIED across periods: `period_idx = epoch % 4`
   - DISTRIBUTED within period: `stride = 12 days`

### Algorithm

```python
def compute_env_start_offsets(period_lengths, n_envs, n_steps, epoch, jitter_minutes, seed):
    # STRATIFIED: interleave periods
    period_idx = epoch % n_periods
    epoch_in_period = epoch // n_periods

    # DISTRIBUTED: stride within period
    stride = period_length // n_envs

    for env_idx in range(n_envs):
        env_offset = env_idx * stride
        jitter = rng.integers(-jitter_minutes, jitter_minutes + 1)
        start = (env_offset + epoch_shift + jitter) % period_length
        starts.append(start)

    return period_idx, starts
```

## Bug Fix: LR Schedule Negative Decay Steps

### The Error

Running `dojo_v3_historical.py --stratified` crashed with:
```
ValueError: The cosine_decay_schedule requires positive decay_steps, got decay_steps=-500.
```

### Root Cause

Misunderstanding of `optax.warmup_cosine_decay_schedule` API.

The `decay_steps` parameter is the **TOTAL** schedule length (warmup + decay), not just the decay portion. Optax internally calculates `decay_steps - warmup_steps` for the cosine portion.

The original code passed `total_steps - warmup_steps` as `decay_steps`:
```python
# WRONG: double-subtracting warmup
decay_steps=total_steps - warmup_steps
# optax then calculates: (total_steps - warmup_steps) - warmup_steps = -500
```

### Fix

1. Pass `total_steps` as `decay_steps` (not the pre-subtracted value):
```python
# CORRECT: let optax do the subtraction
decay_steps=total_steps
```

2. Added guard for edge cases where warmup > total epochs:
```python
if total_steps <= warmup_steps:
    total_steps = warmup_steps + steps_per_epoch
```

3. Reduced default `--lr-warmup-epochs` from 10 to 3 in HISTORICAL_FLAGS for stratified mode (15 epochs/period).

### Files Modified

- `mcts_trader/jax_agent/schedules.py` - Fixed `to_optax_schedule()` method
- `tools/orchestration/dojo_v3_historical.py` - Reduced warmup from 10 to 3

## TASK_064 Part 2: Single-Process Stratified Training

### The Problem

Each period switch in stratified mode spawned a new subprocess:
- JIT recompilation (~2s per period switch)
- Checkpoint save/load overhead
- Environment reinitialization
- **~30% of training time wasted on warmup**

With 4 periods × 15 epochs each, running 4 subprocess meant 4× warmup.

### Solution

Added `--periods-file` to train_jax_fast.py for single-process multi-period training:

1. Load ALL periods' data upfront at startup
2. Store in `period_prices: Dict[int, np.ndarray]`
3. At each epoch, smart_allocation returns `period_idx`
4. If period changed, call `env.set_prices(period_prices[period_idx])`
5. Continue training - no recompilation!

### Usage

```bash
# train_jax_fast.py now supports:
python train_jax_fast.py \
    --periods-file periods.json \
    --smart-allocation \
    --epochs 60

# periods.json format:
{
  "periods": [
    {"start_date": "2018-04-15", "end_date": "2018-10-11", "assets": [...]},
    {"start_date": "2018-10-12", "end_date": "2019-04-01", "assets": [...]},
    ...
  ]
}
```

### Dojo Integration

`run_training_stratified()` now:
1. Generates `/tmp/dojo_periods_{batch}.json` with period definitions
2. Calls `_train_stratified_batch()` - single subprocess for entire batch
3. 60 epochs across 4 periods = ONE process, not 4

**Expected speedup**: ~30% faster (eliminates 3 of 4 warmup cycles per batch)

### Files Modified

- `train_jax_fast.py`:
  - Added `--periods-file` arg
  - Multi-period data loading at startup
  - Period swapping in training loop via `env.set_prices()`
- `dojo_v3_historical.py`:
  - Added `_train_stratified_batch()` method
  - `run_training_stratified()` now uses single-process batch training
