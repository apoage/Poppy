## TASK_128: Critical Training Hang Bug - FIXED

### Problem

Overnight test 3 (full_features with `--use-prediction-loss`) hung at epoch 65. This is a critical bug affecting ~90% of training runs longer than 60 epochs.

**Symptoms:**
- Training runs fine for 50-60 epochs
- Suddenly hangs (no crash, no error)
- GPU util drops to 0%, memory stays high
- Process alive but frozen

### Root Cause Analysis

Debug instrumentation showed hang occurs inside `run_self_play_jax()`, specifically at line 814:

```python
optimal_path = compute_optimal_path(
    jnp.array(log_returns), k=4, method='greedy', transaction_cost=0.0
)
```

**Root cause:** `greedy_lookahead_path` in `path_solver.py` was JIT-compiled with dynamic sequence length `T`:

```python
@partial(jax.jit, static_argnames=['k', 'lookahead'])  # T NOT static!
def greedy_lookahead_path(returns, ...):
    T, n_assets = returns.shape  # Dynamic!
    ...
    jax.lax.scan(step, init_mask, jnp.arange(T))  # Recompiles for each unique T
```

Each unique episode length triggered a new JIT compilation. Over 60-90 epochs with varying truncation points, XLA encountered a problematic sequence length and stalled.

### The Fix

**1. Static max length padding** (`path_solver.py`):
```python
DEFAULT_MAX_PATH_LEN = 512

@partial(jax.jit, static_argnames=['k', 'lookahead', 'max_len'])
def greedy_lookahead_path(returns, ..., max_len=DEFAULT_MAX_PATH_LEN):
    T, n_assets = returns.shape

    # Pad to static length
    padded_returns = jnp.zeros((max_len, n_assets))
    padded_returns = padded_returns.at[:T].set(returns)
    valid_mask = jnp.arange(max_len) < T

    # Scan over static length (single JIT compilation)
    jax.lax.scan(step, init_mask, jnp.arange(max_len))

    # Extract result at actual sequence end
    total_alpha = cumulative_pnl[T - 1]
```

**2. GPU synchronization** (`self_play.py`):
```python
# Before device-to-host transfers
jax.block_until_ready(trajectory_batch['rewards'])
```

**3. Periodic cache clearing** (`train_jax_fast.py`):
```python
if epoch > 0 and epoch % 50 == 0:
    jax.clear_caches()
```

### Replay Buffer JIT Helper (Deadlock Prevention)

Added JIT-compiled helper for buffer updates to prevent potential XLA lock contention:

```python
# replay_buffer.py
@jax.jit
def _update_buffer_slice(buffer, indices, values):
    """JIT-compiled buffer update - avoids full copy overhead."""
    return buffer.at[indices].set(values)
```

**Rationale:**
- Outside JIT, `.at[].set()` creates full array copies (expensive for large buffers)
- Inside JIT, XLA optimizes to in-place ScatterUpdate operations
- Also reduces lock contention with async operations (ThreadPoolExecutor in async_regenerator)

### Root Cause Found: PriceCache Reentrant Lock Deadlock

**The actual bug:** `price_cache.py` uses `threading.Lock()` which is NOT reentrant. When `add_episode()` calls `flush()` while holding the lock, `flush()` tries to acquire the same lock → **DEADLOCK**.

```python
def add_episode(...):
    with self._lock:  # Holds lock
        ...
        if self._flush_counter >= 100:
            self.flush()  # flush() tries to acquire self._lock again = DEADLOCK!

def flush(self):
    with self._lock:  # DEADLOCK - lock already held by add_episode!
```

**Fix:** Change `threading.Lock()` to `threading.RLock()` (reentrant lock) in `price_cache.py:88`.

This explains:
- Why it happens around epoch 60-80 (when ~100 demos accumulate triggering flush)
- Why it's non-deterministic (depends on which envs have positive alpha)
- Why GPU util drops to 0% (Python thread blocked, not GPU issue)

### Investigation Journey

1. **Initial hypothesis:** JAX/XLA recompilation stall (path_solver dynamic shapes)
   - Added static `max_len` padding → didn't fix hang
   - Still useful optimization (prevents recompilation overhead)

2. **Debug instrumentation** pinpointed location progressively:
   - `[HANG-DEBUG] Epoch N self_play START` → hang in self_play
   - `[HANG-DEBUG] lax.scan returned` → not the scan
   - `[HANG-DEBUG] on_episode_complete START` → hang in callback
   - `[CALLBACK-DEBUG] price_cache.add_episode START` → **FOUND IT**

3. **Gemini's analysis** (TASK_128_FINAL_REPORT.md):
   - Correctly identified hang location (`price_cache.add_episode`)
   - Hypothesized async_regenerator thread contention → ❌ not the cause
   - Hypothesized memmap I/O pressure → ❌ not the cause
   - Missed the actual reentrant lock bug

4. **Actual root cause:** Simple Python threading bug - `Lock()` vs `RLock()`
