## Session 3: Physics Dashboard Fix - COMPLETE

### Problem
DS24 Physics tab showing all zeros for:
- Learned parameters (α, β, GARCH)
- G components (G_momentum, G_reversion, G_volatility, G_correlation)

### Root Causes Found

1. **Learned params showing 0**: Dashboard JS had early return when G components missing
   - `updatePhysicsTab()` checked only for G_momentum_mean, etc.
   - If not found, returned early without updating learned params charts

2. **G components not logged**: Only extracting learned params, not running physics forward pass
   - Need actual price data to compute G_momentum, G_reversion, etc.
   - Requires `--use-prediction-loss` flag to collect prices in trajectories

### Fixes Applied

#### 1. Dashboard JS Fix (`tools/DS24/dashboard.js`)
```javascript
// Before: Only checked G components
const hasPhysicsData = ['G_momentum_mean', ...].some(k => data[k]);

// After: Check G components OR learned params
const hasGComponents = ['G_momentum_mean', ...].some(k => data[k] && data[k].some(v => v !== null && v !== 0));
const hasLearnedParams = ['physics_alpha_mean', 'physics_beta_mean', 'garch_persistence']
    .some(k => data[k] && data[k].some(v => v !== null && v !== 0));

if (!hasGComponents && !hasLearnedParams) { return; }
```

#### 2. Physics Forward Pass (`train_jax_fast.py`)
Added actual G component extraction at ds24_level >= 3:
```python
if trajectories and 'prices' in trajectories[0]:
```

## Session 4: GPU Synchronization Bottleneck Fix - COMPLETE

### Problem
GPU utilization dropping from ~80% to ~35% during training. Root cause: "Synchronization Stall" pattern.

### Root Cause
In `mcts_trader/jax_agent/trainer.py`, the training loop was calling `float(value)` on JAX metrics **every single iteration**:

```python
# Line 1107 (before fix)
for key, value in metrics.items():
    if key in history:
        history[key].append(float(value))  # <-- CPU-GPU sync every metric!
```

**Why this kills performance:**
- `float()` on a JAX array forces Device-to-Host synchronization
- CPU stops and waits for GPU to finish current calculation
- Prevents JAX from "pipelining" instructions (queuing next batch while current runs)
- With ~15 metrics tracked, this was 15+ syncs per iteration

### Fix Applied

**1. Store JAX arrays as futures (no sync):**
```python
# Line 1107 (after fix)
for key, value in metrics.items():
    if key in history:
        history[key].append(value)  # Keep as JAX array (async future)
```

**2. Batch convert at end of loop (single sync point):**
```python
# After the loop completes
for key in history:
    if history[key] and hasattr(history[key][0], 'item'):
        history[key] = [float(v) for v in history[key]]
```

### Impact
| Before | After |
|--------|-------|
| ~16 GPU syncs per iteration | 1 sync per iteration (NaN check) |
| GPU utilization: ~35% | GPU utilization: ~80%+ (expected) |
| "Stop-and-go" pipelining | Continuous batch execution |

### VRAM Impact
Negligible (~4 KB for 50 iterations with 20 metrics). JAX 0-d scalar arrays are just pointers to GPU memory.

- `mcts_trader/jax_agent/trainer.py` - Lines 1104-1107 and added batch conversion after loop
