## 82. Server env install — three resolver failures, ended on `pip freeze --no-deps`

Server is Ubuntu 20.04, default Python 3.8 only. Used `uv` (userspace, no sudo).
Server agent caught three internal contradictions in the `pip-compile`-generated
lock that workstation's lenient resolver had accepted:

1. `lightzero` git pin requires `gymnasium[atari]==0.28.0`; we have `gymnasium==1.2.2`.
   → Moved to `requirements.nodeps.txt` for `--no-deps` install. Worked locally
   but the next conflict was right behind.
2. `tensorflow-metadata==1.17.2` needs `protobuf>=4.25.2`; we have `protobuf==4.21.12`.
   → Confirmed the lock is generally inconsistent. Switched approach entirely.
3. `torch==2.5.1+cu121` not on PyPI. Added `--extra-index-url`, then uv refused
   to mix indexes (first-index strategy on `certifi`). → Dropped `+cu121` suffix;
   plain `torch==2.5.1` from PyPI bundles CUDA via the `nvidia-*-cu12` wheels.

**Final approach**: `pip freeze > requirements.frozen.txt` on workstation, install
with `uv pip install --no-deps -r requirements.frozen.txt` on server. Sidesteps
resolution entirely. Workstation is the operational truth; server reproduces it
byte-for-byte (modulo recompiles).

**Discipline**: future deps go on workstation first, then `pip freeze`, then
deploy. `requirements.frozen.txt` is workstation-mastered authoritative state.

Python on server is now 3.10.20 (matches workstation 3.10.14).

### What this rules out

- Code-level bug in `train_phase2.py` rank-head path — workstation has the

- Numerical issue (no NaN, same loss values to 3 sig figs as the server

### What it leaves

Server-side environment differential. Strongest candidates, roughly ranked:

1. **Multi-process contention.** Server ran no_aux on GPU 0 *in parallel*
   with no_rank on GPU 1 and minimal on GPU 2. Each held ~21 GB VRAM. Host

   hit only under that pressure. **Best fit to evidence:**
   - 347 threads in futex_wait → process is idle waiting (consistent with

   - Not deterministic on workstation (single process, single GPU)
   - Other two variants also at E18 boundary, but only one deadlocked —
     consistent with a rare race
2. **Kernel/driver version differential** server vs workstation (CUDA
   driver, glibc futex behavior). Not yet inspected.
3. **Latent rank-head bug** that only surfaces under specific
   sample-timing. Possible but workstation should have a non-zero hit rate

|---|---|---|---|---|

| `a1b1_repro` | ✅ 200 epochs | total=6.6027 @ E196 | ~2h19m (23:15→01:35) | dropped 01:35 |

**TASK_742 root cause: multi-process contention.** Definitive evidence:
- Original failure was 3 parallel train_phase2.py processes (no_aux + no_rank + minimal) sharing host. Only no_aux deadlocked.
- 1-process workstation repro (yesterday §87) — no deadlock.
- 2-process server overnight (a1b1 + no_aux_solo, both rank-head ON) — no deadlock.
- Threshold appears to be **≥3 concurrent train_phase2.py instances** on the host.

The rank-head code path itself is fine. The deadlock is a host-level resource contention bug under high concurrency — most likely a shared resource (JAX compile cache write lock, CUDA driver synchronization, NCCL init) that doesn't gracefully serialize at 3+ processes.

**Operational rule going forward:** run ≤2 parallel `train_phase2.py` processes per host. For full TASK_737-style sweeps with 4 GPUs, stagger startup with a 30-60s gap or run serially. Better: launch each pair sequentially so each batch produces a baseline reference.
