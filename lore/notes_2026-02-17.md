## TASK_676: Streaming Encoder Research — Complete

Deep research into replacing the windowed encoder with a streaming architecture.

### Critical Discovery

The current `AssetTransformerEncoder` (`trm_encoder_v2.py`) has **no temporal processing**.
It flattens `(60 timesteps × 27 channels) = 1620` features into a Dense layer. Temporal
ordering is completely destroyed — a spike at t=0 and t=59 are indistinguishable.

This means:
- KV-caching is irrelevant (no temporal attention to cache)
- The "streaming" task is about **adding** temporal processing, not converting it
- The current encoder is leaving temporal information on the table

### Approaches Researched

| Approach | JAX Ready | Verdict |
|----------|-----------|---------|
| KV-caching | Built-in Flax | NOT APPLICABLE (no temporal attention) |
| **minGRU** | ~30 LOC pure JAX | **RECOMMENDED for Poppy encoder** |
| RG-LRU (Griffin) | Production (Google) | Fallback if minGRU lacks capacity |
| S5 SSM | Official JAX | Alternative (complex eigenvalues for cycles) |
| Mamba-1 | Already in codebase | **Best for Bella (diff_teacher)**, overkill for Poppy |
| Mamba-2 | Alpha JAX | Future option |
| xLSTM | Official JAX | Overkill for T=60 |
| RetNet/RWKV | No JAX impl | Not viable |

### Recommendation: minGRU for Poppy, Mamba stays for Bella

**Poppy's encoder** (easy training pipeline, T=60):
- Replace `flatten → Dense` with `Dense(27→32) → minGRU(32) → cross-asset attention`
- ~40 lines of code, `lax.associative_scan` for parallel training, trivial recurrent step
- Preserves temporal ordering (quality improvement, not just speed)
- Oracle multipass: ~3-4× speedup (O(1) per step vs O(60) re-encoding)

**Bella** (diff_teacher market generator):
- Mamba is already there and correct — SSM with selective scan, content-aware filtering
- Full `MambaBlock` + `CausalConv1D` + sequential/parallel scan implementations
- Right tool for longer sequences and generative modeling

### Implementation Plan

Phase 1: Build `trm_encoder_v3.py` with `StreamingAssetEncoder` (minGRU core)
Phase 2: Wire into multipass oracle for streaming inference
Phase 3: Benchmark against v2 baseline

## TASK_678: Geometric Manifold Rectification — Research + Adversarial Review

Reviewed paper `arXiv-2602.13045v1` (Wang, Li, Jia) on GMR for imbalanced classification.
Core idea: majority class topologically intrudes into minority manifold. Fix with
inverse-distance weighted kNN confidence + asymmetric cleaning.

### Relevance to Poppy

63:1 HOLD-to-TRADE imbalance. Current weighting is purely label-based (trade_strength
from oracle). GMR adds the **geometric** dimension — where does a sample sit relative
to its structural neighbors? Two HOLDs with identical oracle labels can have very
different informational value depending on their market structure context.

### Adversarial Review — 4 Critical Flaws Found

| Issue | Problem | Resolution |
|-------|---------|------------|
| **CRIT-1: Latent Collapse** | Online GMR in latent space creates death spiral — turtle encoder sees TRADEs as outliers, downweights them, learns even less | Use **raw log-returns** for distance metric, not model latents |
| **CRIT-2: Batch Sparsity** | 63:1 imbalance → ~0 TRADE neighbors per asset in a batch → kNN votes all-HOLD | Compute kNN **per-episode in buffer**, not within batch |
| **CRIT-3: Soft Targets** | GMR assumes discrete y∈{0,1}, but multipass oracle gives continuous soft targets | Replace discrete voting with **KL-divergence consistency** |
| **CRIT-4: JIT Overhead** | 16K×16K distance matrix = 1GB per step, kills throughput | Run offline in **OnTheFlyGenerator background thread** |

### Revised Approach: Buffer-Level Structure-GMR

Only viable path: offline cleaning in `_refill_buffer()` using raw price structure.

```
Per episode, per asset:
  1. Compute cosine distance on log-return curves across timesteps
  2. kNN (k=7) per timestep using return structure
  3. KL-divergence between sample's soft target and neighbors' soft targets
  4. Asymmetric rectification:
     - High-KL HOLDs → soften toward neighbor consensus (blend up to 50%)
     - High-KL TRADEs → flag but protect (γ=10% cap, blend up to 30%)
     - Low-KL everything → keep as-is
  5. Skip curriculum levels < 5 (no structure to rectify on noise)
```

Key insight: **soft rectification, not hard removal**. Blend conflicting labels toward
neighbor consensus rather than flipping or deleting. This is "Softer GMR" for the
soft-target regime.

## TASK_679: Agreement Plateau at 52.5% — Signal Density Problem

### Diagnosis

Training launched 2026-02-16 23:03 (post TASK_674-677 fixes). Reached epoch 618 and hard-plateaued.
CSV data tells the story:

| Metric | Value | Meaning |
|--------|-------|---------|
| **oracle_hold_ratio** | 98.9% | Oracle says HOLD on 98.9% of all (batch × 64) positions |
| **agree_hold** | 95.8% | Model nails holds |
| **agree_trade** | **9.4%** | Model is random on trades (below 20% chance baseline for 5 actions) |
| **balanced_agreement** | 52.6% | = 0.5 × 95.8 + 0.5 × 9.4 |
| **pred_hold_ratio** | 95.7% | Model predicts slightly fewer holds than oracle |
| **adaptive_trade_weight** | 64.0 (max) | TASK_675 gradient fix active |
| **best_agreement** | 53.4% | Peaked early, flat for hundreds of epochs |
| **global_agreement** | 0.0 | Broken metric (legacy, always 0) |
| **grad_norm** | ~0.17 | Stable, not exploding/vanishing |

The TASK_675 gradient drowning fix solved **gradient magnitude** — trades get equal gradient mass.
But the **density problem** remains: with k=1 oracle on 64 assets, only ~0.7 assets per step
have trade signals. Per batch of 1024 × 64 = 65,536 positions, only ~700 are trades. The model
can't learn WHICH asset to trade AND what direction from this sparse signal.

9.4% trade accuracy is **below random** (20% for 5 classes). The model is actively confused,
not just undertrained. It sees too few trade examples to form distinctive patterns.

### Root Cause: Threshold × Assets × k Interaction

```
min_alpha_threshold = 0.001
oracle_lookahead = 20
effective_bar = 0.001 × 20 = 0.02 (2% cumulative absolute return over 20 steps)
```

Most assets don't move 2% in 20 steps of synthetic data. Result: oracle produces ~0.7 trades
per step across 64 assets, yielding 98.9% hold ratio.

### Fix Applied: Lower `min_alpha_threshold` (0.001 → 0.0005)

`easy_config.py:58` — effective bar drops from 2.0% to 1.0% cumulative over 20 steps.

| Threshold | Effective bar (20 steps) | Est. trade density | Notes |
|-----------|--------------------------|-------------------|-------|
| 0.001 (was) | 2.0% | ~1.1% | Too sparse |
| **0.0005 (now)** | **1.0%** | **~2-3%** | 2-3× more trades, still meaningful alpha |
| 0.0003 (aggressive) | 0.6% | ~4-5% | Risk: noise trades |

This is conservative — 1% absolute return over 20 steps is still real signal, not noise.
Expected impact: trade density roughly doubles/triples, giving the model enough examples
to start distinguishing trade contexts from hold contexts.

### Rejected: Increase `oracle_k`

k>1 would break the value head. The model executes 1 trade/step. Training on multi-trade
oracle would teach value head unrealizable multi-asset profits → MCTS collapse downstream.
(Documented in easy_config.py comment, confirmed by k>1 experiment history.)

## Research: Trade-Biased Sampling (complementary to TASK_679)

### The Idea

Instead of uniformly sampling timesteps from the episode buffer, **bias toward windows where
the oracle actually traded**. Current sampling is uniform across the episode — but if only
5 of 400 timesteps have trade signals, 98.75% of training signal is pure hold reinforcement.

### How It Would Work

In `OnTheFlyGenerator.generate_batch()`:

1. **Index phase** (during `_refill_buffer`): For each episode, build a sparse index of
   timesteps where oracle produced a trade action. Store as `trade_timesteps: List[int]`
   per buffer slot. Cost: negligible (one argmax scan per episode, ~0.1ms).

2. **Sampling phase** (during `generate_batch`): Instead of uniform `offset` selection,
   use weighted sampling:
   ```
   P(timestep t) ∝ 1.0 + trade_boost × has_trade(t)
   ```
   With `trade_boost=5.0`, a timestep with a trade is 6× more likely to be sampled.
   Trade windows appear ~6× more often → model sees ~6× more trade examples per batch.

3. **No oracle quality change**: The oracle labels stay identical. We're not changing
   WHAT the model learns, just HOW OFTEN it sees trade examples. Holds still appear
   (they're the majority of every window), but windows with trade signals dominate.

### Expected Impact

| Metric | Current | With trade-biased sampling |
|--------|---------|---------------------------|
| Trade examples per batch | ~700 / 65,536 (1.1%) | ~4,000 / 65,536 (~6%) |
| Gradient ratio (trade:hold) | 1:1 (TASK_675 fix) | 1:1 (unchanged) |
| Data diversity | Full episode coverage | Slight bias toward volatile windows |
| Oracle quality | Unchanged | Unchanged |

### Risk Assessment

**Low risk**: This is essentially importance sampling for the minority class. The model
still sees all curriculum levels and market conditions. The only bias is toward timestamps
where something interesting happens — which is exactly what we want the model to learn.

**Interaction with TASK_678 (GMR)**: Complementary. GMR cleans label quality at the
buffer level, trade-biased sampling increases how often clean trade examples are seen.
They address different axes: GMR = label quality, sampling = label frequency.

**Interaction with TASK_679 (threshold)**: Multiplicative. Lower threshold produces more
trade timesteps, biased sampling shows them more often. Combined effect: ~6-10× more trade
gradient signal vs current baseline.

### Implementation Complexity

~30 lines of code in `train_easy.py` (OnTheFlyGenerator). No architectural changes,
no new dependencies, no JIT recompilation. Can be toggled via config flag.

### Not Implementing Yet

Want to see TASK_679 (threshold change) impact first. If threshold alone breaks the plateau,
sampling bias may not be needed. If plateau persists at ~55-60%, sampling bias is the next lever.
