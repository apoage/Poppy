## §209 — The TASK_804 front-end verdict: NULL on Alpha, exactly as predicted — and why that is not a branch-C epitaph

**What was believed before — and it was a prediction, not a hope.** TASK_801 was specced with the null
written in: "predicted null on Alpha… built anyway because it is the control arm the real-vs-random gate
requires." The whole project's scar tissue agreed — every classifier/encoder/perception-sharpening
mechanism since TASK_738 has come back null-or-worse on deployment Alpha
([[project_classifier_alpha_anti_correlation.md]], [[project_single_mechanism_exhausted.md]]). So the
front-end arms were never the bet; they were the *gate* the bet has to pass through. The operative
control is `shift_fe`: a per-asset **cyclic shift** of the real token timeline
(`rolled[i] = real[(i−Δ_a) mod N]`, `Δ_a` seeded per `(asset, seed 804)`). It preserves the token
frequency multiset, the run-lengths, and the grammar — destroying **only** alignment with the concurrent
price window. So the gate reads cleanly: `real_fe > shift_fe` ⟺ aligned token *content* carries signal
beyond capacity/structure. Anything else and the perception side is null.

**What happened.** Final eval-MCTS sims=16 `avg_alpha`, read from
`runs/804_token_arms/eval_*/benchmark.json` (`summary.avg_alpha`), across all three seeds:

| seed | raw | real_fe | shift_fe |
|------|-----|---------|----------|
| 7    | (raw_seed7 cursed, missing) | 0.0641 | 0.0768 |
| 13   | 0.0573 | 0.0558 | 0.0605 |
| 23   | (raw_seed23 training now)   | 0.0684 | 0.0704 |

The shuffled control wins, quietly, everywhere: **shift_fe ≥ real_fe in all three seeds** — s7 +1.27pp,
s13 +0.47pp, s23 +0.20pp. And the one head-to-head we have against the no-token baseline,
`real_fe_seed13 − raw_seed13 = −0.15pp`, sits on zero. The token **front-end does not beat its own
shuffled control.** That is the perception-side null, landed.

**The confirmation (not a reversal).** This overturns nothing — it *confirms* the prediction TASK_801
carried into the run. The honest magnitude matters: the alphas cluster in a ~2pp band (5.6–7.7%), and
shift beats real by sub-pp to ~1pp margins — comfortably inside the project's own "≤5pp single-seed =
noise" rule. So the correct reading is **"no perception-side signal detected,"** consistent with the
prior, and explicitly **not** "tokenisation measurably *harmed* the trader." The control didn't lose to
real; real failed to clear the control. A clean negative, written as one.

**The framing that must not slip (this is the part Bloom and the next agent both need).** The front-end
null does **not** retire branch C. Branch C's actual hypothesis was never that token *perception* adds
Alpha — it is that token value, if it exists, lives on the **planning side**: token-grounded *dynamics*
(TASK_802's NextTokenHead), the standing hypothesis since TASK_761. The TASK_804 spec wrote the decision
rule for exactly this case (line 75): "arms 2–3 null but 4 > 5 with margin → token value is planning-side."
Arms 4–5 (`real_dyn` vs `shift_dyn`) test that surface, and at the moment the front-end verdict came in
they **had not run**. Conflating "token perception adds no Alpha" (expected, now shown) with "branch C
nulls" (untested) would retire the branch on evidence that never touched its real claim. The front-end
pass is necessary infrastructure-clearing — proof the gate works and the control is honest. The dynamics
pass is the bet.

**Lesson.** A predicted null that lands as predicted is *information about the gate, not the
hypothesis.* The front-end arms proved the cyclic-shift control discriminates and that the perception
surface is flat — both prerequisites for trusting whatever arms 4–5 say next. Spend the result there;
do not let a control arm's expected null get quoted as the structural bet's obituary.

## §210 — Arms 4–5 launched: the dynamics test, the one that actually counts

**State on entry.** TASK_802 dynamics code verified live on the server before launch: all four
token-path files byte-identical local↔server, `muzero_model.py` sha `b4a02f58…`, the NextTokenHead +
`use_token_dynamics` plumbing intact. Front-end campaign still finishing its tail (raw_seed23 training,
raw_seed7 cursed).

**What the arms are.** `real_dyn` = `real_fe` front-end flags + `--use-token-dynamics
--token-dynamics-weight 0.1`. `shift_dyn` = `shift_fe` (cyclic-shift null) flags + the same dynamics
flags. Both **reuse the already-built token-cache disk artifacts** — real timelines `d6a718dd…`, shift
timelines `b55f18f6…` — so cache HIT is confirmed (833 per-asset timelines loaded instantly from disk,
no cold-annotate; the 47-min wall from §208 stays buried). Eval is safe **unchanged**: `benchmark_easy`
auto-detects the frontend from the saved checkpoint config, and the `next_token_head` is **eval-inert** —
the MCTS/trading path never reads `next_token_logits`, and flax tolerates the extra params. A dynamics
checkpoint therefore evals *exactly* like its `real_fe`/`shift_fe` twin; nothing in the scorecard path
changes.

**Mechanics (re-entry anchors).** A self-contained GPU-2 runner, `/tmp/dyn_solo.py`, **trains and evals
on GPU 2** so it never contends with the front-end retry runner (`804_solo`, GPU 1 train / GPU 3 eval).
Per-run frozen-log watchdog + systemd-scope reap + 3 retries — the same discipline as the front-end
`solo_retry` runner, including the `_reap_scope` orphan fix (`78ccb70`) that the §208 cascade forced.
Namespaces are disjoint by design: run-dirs `real_dyn_seed*` / `shift_dyn_seed*`, units `804dyn_*`, tmux
`804_dyn`. TASK_742-safe — only **two trains total** concurrent (raw_seed23 on GPU1, real_dyn_seed7 on
GPU2). **Seed-major order** (`real_dyn` + `shift_dyn` per seed, 7 → 13 → 23) so each seed's within-pair
`real_dyn − shift_dyn` signal — the branch-C diagnostic — completes as early as possible. Launched
2026-06-18 ~22:38, gated (per user decision) on `real_fe_seed13` finishing first so the front-end
scorecard was complete bar the cursed raw_seed7.

**The decisive next gate.** `real_dyn > shift_dyn` with margin — concretely, arm4−arm1 paired mean
Δα ≥ +3pp, no seed < −5pp, and arm4 > arm5 — would be **branch C's first real positive since the entire
token program began**, and graduates it to checkpoint-lineage training. `real_dyn ≈ shift_dyn` = branch
C nulls *on the surface it was actually built for*, and **then** the negative is publishable as
branch-wide: the candle-language panel stands as measurement infrastructure, it does not move the trader.
Either outcome is a result; the dynamics arms are the test that counts, and this is the first time the
planning-side claim is on the bench.

**Loose end (do not chase).** `raw_seed7` is the recurring intrinsic seed-7 Stage-B wedge
([[project_seed7_stageb_wedge]]) — specifically raw-arm × seed-7 (`raw_s13` and all the seed-7 *token*
arms completed fine, which localises it to that one cell). The front-end retry runner will burn its 3
retries on it and give up. Expect the final shape to be a **2-seed (13, 23) Δα-vs-raw** result plus the
**complete 3-seed shift-vs-real direction**. That is an acceptable shape — do **not** burn more GPU
chasing `raw_seed7`.

**Lesson.** The expensive irreversible resource (GPU) is fully booked by two campaigns at once without
violating TASK_742 only because the lanes are physically partitioned (GPU 1/3 front-end, GPU 2 dynamics)
and the cache wall is already paid down to a disk HIT. Seed-major ordering is the cheap scheduling choice
that makes the *first* branch-C diagnostic readable as early as possible, instead of last.
