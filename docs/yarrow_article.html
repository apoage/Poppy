Your AI Agent Swarm Is a Mob. Mine Is an Apothecary.

Why constraints — not capabilities — make multi-agent AI systems work

Everyone is building multi-agent AI systems right now. Claude Code Swarms. OpenClaw. AutoGPT descendants. The pitch is always the same: throw more agents at the problem. More parallelism. More throughput. More swarm.

I went the other direction. I built an apothecary.

The Problem With Swarms

A swarm is a mob with good intentions. Every agent can do everything. Every agent talks to every other agent. The lead agent is just another agent with a fancier prompt. Nothing stops the researcher from editing code. Nothing stops the implementer from deciding scope. Nothing stops any of them from confirming each other's hallucinations.

Claude Code Swarms — Anthropic's new multi-agent feature — is impressive engineering. Multiple Claude instances coordinate through a shared task list, direct messaging, and a lead agent that delegates work. But architecturally, it's the same model talking to itself in parallel. You get parallelism, not diversity. Speed, not reliability.

OpenClaw takes a different approach — general-purpose life automation through messaging apps. It can manage your email, calendar, and shell commands. But its "multi-agent" mode is really multiple isolated instances with routing rules. They don't collaborate; they coexist.

Neither system addresses the fundamental question: how do you make reliable decisions when your agents are powerful but unpredictable?

Dangerous Materials Require Protocol

An apothecary works with belladonna, which dilates pupils for eye exams — or kills you. Poppy, which stops unbearable pain — or stops your breathing. Foxglove, which regulates your heartbeat — or stops it entirely.

These aren't dangerous because they're weak. They're dangerous because they're powerful. The entire profession of pharmacy exists because powerful substances demand protocol. Not suggestions. Not "best practices." Hard boundaries that you cannot cross.

  • The harvester gathers the plant. Doesn't decide the dose.
  • The apprentice grinds and sorts. Doesn't write the prescription.
  • The apothecary reads symptoms, decides treatment. Never touches the mortar.
  • The compounder mixes exactly what's prescribed. Never improvises.

Remove any one of these boundaries and someone dies. That's not bureaucracy. That's safety engineering for dangerous tools.

Large language models are the dangerous materials. Powerful, creative, capable of extraordinary insight — and capable of confidently fabricating nonsense. A swarm just throws them at the problem and hopes the aggregate is better than any individual. An apothecary shop handles them with the respect they require.

The Architecture

The system is called Yarrow — named for the wound-healing herb used in the I Ching for divination. A compound flower where dozens of tiny blooms function as one. It doesn't cause action. It controls the response.

The Roles

Harvesters (5–7 different LLMs from different providers) independently scan code, data, or any context. They write structured findings to a shared database. They never see each other's work. They never edit anything. They're gatherers — nothing more.

The Apprentice (a cheap, fast model) deduplicates findings, clusters related issues, and computes ensemble confidence scores. It's a filter — it preserves everything but organizes the noise so the orchestrator's context window stays clean.

The Apothecary (the strongest available model) reads the cleaned clusters, validates them against source material, prioritizes, and writes precise specifications for what should be done. It decides. It prescribes. It never implements.

The Compounder (a strong model with tool access) reads one specification at a time and implements it exactly as written. If the spec is ambiguous, it asks — it doesn't interpret. If the fix requires a larger scope than specified, it reports back — it doesn't expand. Discovered issues go into its report, not into the code.

Remove any one of these and the system degrades toward "one agent doing everything" — which is what every other system already is.

The Key Innovation: Ensemble Voting With Precision Tracking

This is what makes Yarrow fundamentally different from both Claude Code Swarms and OpenClaw.

When you use Claude Code Swarms, you're running the same model multiple times. You get parallelism, but every instance shares the same blind spots, the same training biases, the same failure modes. It's the AI equivalent of asking the same person the same question five times.

Yarrow uses 5–7 different models from different providers. Gemini, Claude, GLM, Kimi, DeepSeek, OpenAI — each with genuinely different training data, different architectures, different failure modes. When three of them independently flag the same issue without seeing each other's work, that's real signal.


1 harvester flags it              → low confidence, investigate
2 harvesters flag same thing      → likely real
3+ harvesters flag same thing     → high confidence, fast-track

But raw vote counting isn't enough. Each harvester has a tracked precision score based on historical performance:


agent_stats:
  gemini:    { findings: 156, confirmed: 47, precision: 0.30 }  # noisy but creative
  claude:    { findings: 62,  confirmed: 45, precision: 0.73 }  # reliable
  glm:       { findings: 88,  confirmed: 35, precision: 0.40 }  # middle ground

A solo finding from a high-precision agent gets trusted. A solo finding from a noisy agent needs corroboration. The system learns which of its own components to trust — and how much.

Communication: Files, Not Wires

All inter-agent communication happens through the filesystem. JSON files for findings. Markdown files for task specs. A SQLite database for queries. No WebSockets. No message queues. No direct API calls between agents.

This sounds primitive. It's actually the strongest design choice in the system.

  • Inspectable — you can read any message between any agents at any time
  • Git-trackable — version control the decision process itself, not just the code
  • Crash-proof — recovery is "re-read the files." That's it.
  • Model-agnostic — any model that can read and write JSON participates
  • Debuggable — when something goes wrong, the entire evidence trail exists on disk

The database mirrors the filesystem. Either can be rebuilt from the other. Simplicity is a feature when your agents are the complex part.

User Control: The Gear Shift


PLAN MODE  ──→  APPROVAL  ──→  YOLO MODE  ──→  PLAN MODE
(research)      (you decide)    (autonomous)     (cycle)

The user controls mode transitions. The system never self-promotes to autonomous execution. When the executor encounters uncertainty, it auto-stops and asks. This isn't a limitation — it's the whole point. The system is powerful precisely because it knows when to stop.

The Generalization

Yarrow was built for code review and bug hunting. But the hierarchy has nothing to do with code. The pipeline is:

  1. Direct — orchestrator tells harvesters where to look
  2. Harvest — N models independently scan context
  3. Reduce — assistant deduplicates and scores
  4. Decide — orchestrator validates and writes action specs
  5. Approve — user reviews
  6. Execute — implementer follows specs precisely
  7. Verify — orchestrator checks results

This works for anything. Architecture design. Research analysis. Trading decisions. Security audits. The only things that change per domain are the directive format, the finding schema, and what the executor does with approved specs.

It's not a tool. It's a decision-quality amplifier.

The Name

The project uses an apothecary naming theme. Not because it sounds cool — because it encodes the architecture.

Every component is named after a medicinal plant or apothecary role. Poppy (the MCTS trading agent — dreams via planning). Belladonna (the market generator — vision of unseen markets). Foxglove (the training system — regulates the heartbeat of learning). And Yarrow — the orchestration layer that controls the healing response.

All of these plants heal or kill depending on how carefully you work with them. That's not a theme. That's a worldview. And it's the right worldview for working with large language models — powerful, unpredictable tools that demand protocol, not faith.

Yarrow is open-source and designed to run on top of existing AI coding tools. The architecture is documented at the project repository.
