# BUGHUNT 769 — F2 PopArt pre-clip fix (commit 95fcf98)

Read-only adversarial review of TASK_769 — flag-gated reorder of the
`[-10, 10]` value-target clip from BEFORE PopArt normalization to AFTER.
Code commit `95fcf98`; SPEC status-line update `230a145`. Smoke ran on
workstation RTX 3090 2026-05-23 ~05:00–05:47 UTC+2 and claimed bit-identity
of `pre_popart` to pre-patch baseline. This pass: confirm bit-identity by
inspection, verify the 4 gated sites are byte-equivalent in the
`pre_popart` branch, look for behavioural footguns under `post_popart`,
and check the documentation surface.

Verdict at a glance: the **code change is structurally clean**. All 4
clip-gate sites reduce to literal pre-patch expressions under `pre_popart`
(direct Python branch on a JIT-captured string constant — no `lax.cond`,
no extra cast, no dtype change). Bit-identity is provable by inspection
and confirmed by smoke `A2 == A0` at 6-decimal CSV precision. No P0/P1
correctness bugs found. Three **P2** documentation / surface findings
(stale line numbers in SPEC body, missing logger line for the new mode,
amended-draft commit hash artefact in SPEC). Three **P3** behavioural
caveats worth knowing about but not fixing: (a) early-epoch post-norm
clip saturation under `post_popart`; (b) `:637` immediate-reward
unconditional clip means `post_popart` is incomplete for `td0` mode;
(c) the rs200 mechanism gate tests the **nstep** path only — oracle
mode's `oracle_scaled = oracle_values * value_scale` is not coupled to
`reward_scale`, so `rs200` exercises the per-step n-step clip exclusively.

### F4 (P3 — behavioural, documented in SPEC but worth surfacing): `:637` left unconditional means `post_popart` is INCOMPLETE for `td0` mode

- `train_phase2.py:637` — `rewards = np.clip(step_pnl * self.config.reward_scale, -10.0, 10.0)` (unconditional)
- `train_phase2.py:1289` — `r_step = rewards_dynamics` (td0 branch reads the array clipped at `:637`)
- `train_phase2.py:1292-1297` — td0's `td_target_raw = r_step + config_discount * v_next`, gated post-clip on `value_clip_mode == "pre_popart"`
- Net effect: in `post_popart + td0`, `td_target_raw` is unclipped at the sum step but `r_step` is STILL pre-clipped at `:637`. PopArt sees a partially-uncensored distribution. For oracle and nstep (the 769 cells), this is correct — neither uses `rewards_dynamics` in the value path. For td0, the F2 fix is structurally incomplete.
- SPEC documents the choice at `:78` and the commit message at `:36-43` of `95fcf98` explains it (CE target safety, td0 not a 769 cell). This is **intentional, not a bug**.
- Why P3, not P2: SPEC and commit message both call this out, and td0 isn't promoted to a 769 variant. Surfacing for the bughunt record so a future "extend 769 to td0" agent knows the `:637` site is a load-bearing scope decision, not an oversight.
- Fix (only if td0 ever gets variants): a td0 variant would need to either widen `:637` itself (with the dynamics-CE crash protected by a separate categorical-support clip just before `:1328`'s `scalar_to_categorical`) or use a separate `rewards_unclipped` array threaded through the batch dict.

### F5 (P3 — behavioural, documented in SPEC): early-epoch post-norm clip saturation under `post_popart`

- `train_phase2.py:1268, 1286, 1299` — unconditional `td_target_norm = jnp.clip(td_target_norm, -10.0, 10.0)`
- `mcts_trader/jax_agent/popart.py:75-82` — first batch (`state.count == 0`) sets `new_var = batch_var + 1e-8`, so PopArt initialises to batch statistics on the very first update.
- But the JIT step at `train_phase2.py:1939-1940` reads `popart_state` BEFORE that batch's update — so the first JIT step uses `popart_mean=0, popart_std=1` (init values), normalises the (unclipped, potentially large) raw target by 1, and then `:1286` clips it to [-10, 10]. Result: first batch's value loss can be CE against a clipped-at-±10 normalized target — a near-flat 401-bin distribution at one endpoint, which is the maximum-entropy worst case.
- After batch 1, PopArt's `popart_std` jumps to the first batch's std (which under nstep at `reward_scale=200` could easily be ~30+), and subsequent batches' `td_target_norm` collapses to <±1 — within support, fine.
- Impact: a 769 `post_popart` run will look "spiky-bad" at step 1 then settle. Value-loss curve will jump-down by ~1-2× between step 1 and step 2. SPEC §93 calls this out as "early-training failure mode: small `popart_std` can make `post_popart` ride the post-norm clip for the first epochs — recoverable, not a NaN, but value loss looks high early."
- Why P3: documented, recoverable, doesn't break anything — but a server-agent monitoring a 769 launch could panic at the first metric if they don't know to expect it. Worth a single sentence in `result.md` when 769 closes.

### F6 (P3 — scoping): `rs200` mechanism gate tests the **n-step** F2 path only — oracle's `oracle_scaled` is uncoupled from `reward_scale`

- `train_phase2.py:1259` — `oracle_scaled = oracle_values * value_scale` (where `value_scale = 2.0`, NOT `reward_scale`)
- `train_phase2.py:644` — `oracle_values` is `(oracle_cum_pnl[end_idx] - oracle_cum_pnl[decision_indices])`, raw cumulative PnL with no `reward_scale` multiplier
- `train_phase2.py:679, 689` — n-step `per_step_r = per_step_pnl * self.config.reward_scale` (then gated clip)
- The 762 Wave 1 rs200 regression that motivated 769 was on `value_target_mode="nstep"` (verified against `runs/762_reward_shaping/rs200_seed_13/stage_b_config.json` — `"value_target_mode": "nstep"`)
- Implication: `769-fix-rs200` exercises the F2 fix on the n-step pipeline (which IS what 762 Wave 1 ran). If a future "769-fix-rs200 oracle" cell is proposed, the rs200 axis does NOT directly stress the F2 clip in oracle mode — the oracle target's saturation depends only on raw PnL magnitude × `value_scale=2.0`. The rs200 mechanism gate in SPEC §44-48 should be read as "for the n-step path"; SPEC nstep/oracle conflation at §17 (the abstract "reward_scale multiplies into the clipped quantity") is true for n-step only.
- Why P3: doesn't break the experiment — the 762/769 chain is intrinsically n-step — but if oracle ever gets a `reward_scale` variant or someone moves a hypothesis cell, this asymmetry is worth knowing. SPEC §103-105 says "Wave 1 was nstep", so the lore is internally consistent; only the SPEC §17 abstract is loose.

## Verified clean

- **Bit-identity of the 4 `pre_popart` gate branches.** For each gated site (`:688-689`, `:1265-1266`, `:1283-1284`, `:1296-1297`), the `if value_clip_mode == "pre_popart":` body is a literal `jnp.clip(x, -10.0, 10.0)` (or `np.clip` at `:689`) — exactly the pre-patch expression. The Python conditional is evaluated at JIT trace time (closure-captured string, not a JAX traced value), so when `pre_popart` is in effect the traced XLA graph is identical to pre-patch by construction. The smoke's `A2 == A0` at 6-decimal CSV precision is the empirical proof; the code-inspection argument is the structural proof. C2 vs C0 oracle 5-6th-digit drift is consistent with cuDNN autotune kernel selection (the smoke train-times A=27s vs A2=9.4s for the same 50 steps are a direct fingerprint of different cuDNN kernels being selected for the cold-start vs hot run).
- **No leak between modes via `td_target_raw`.** In both branches the assignment `td_target_raw = oracle_scaled` is literally the same statement; the difference is whether `oracle_scaled` was clipped above. In `pre_popart`, `oracle_scaled` is clipped, so PopArt sees the same clipped distribution as canon. In `post_popart`, `oracle_scaled` is unclipped, so PopArt sees the true distribution. No cross-pollination — the user's concern at item #1 about the `td_target_raw = oracle_scaled` line leaking into `pre_popart` is unfounded; that assignment is identical in both modes, the difference is exclusively upstream.
- **PopArt EMA absorbs the wider distribution.** `popart.py:78-82` — `new_var = (1 − β) * var + β * batch_var` with β = 0.0003. Batch spikes are weighted 0.03%; sustained-wider-distribution converges via EMA over ~1/β ≈ 3300 batches. Variance is bounded above by sustained batch variance — no unbounded growth. `popart.py:81` guards `new_var ≥ 1e-8` so the divisor in normalize doesn't collapse.
- **Closure capture handles missing config field.** `train_phase2.py:1050` uses `getattr(config, 'value_clip_mode', 'pre_popart')`. The config is always built fresh via `Phase2Config(**filtered)` (`:2574`) or `get_phase2_config(...)` (`:2571` → `phase2_config.py:307`), both of which apply the dataclass default `"pre_popart"`. A pre-769 checkpoint resumed via either path inherits the default — the canon path. Verified.
- **`.git-training-worktree/phase2_config.py` and `train_phase2.py` carry the patch.** Worktree HEAD is `1a1c79a` (deploy commit, training branch); both files have `value_clip_mode` and the 4 gates. The SPEC §92 gotcha about a stale worktree is not present in this state — deploy contract worked.
- **`stage_b_config.json` records `value_clip_mode`.** Verified against `runs/000_smoke/769_value_clip/B_post_nstep/stage_b_config.json`. Reproducibility preserved via the existing config-dump path (`train_phase2.py:1803-1807`).
- **MCTS search denormalization is unaffected.** `train_phase2.py:1877-1879` sets `search.value_scale = float(jnp.sqrt(popart_state.var + 1e-8))` and `search.value_shift = float(popart_state.mean)`. In `post_popart`, PopArt holds larger var → search denormalizes by a larger factor → matches the larger normalised-space value head outputs. Composition is correct; no eval-time threading of `value_clip_mode` needed (and the patch correctly does not add any).
- **All `[-10, 10]` clip sites in `train_phase2.py` accounted for.** `grep -n 'jnp.clip\|np.clip' train_phase2.py` shows 10 hits: `:83, :86` (scalar_to_categorical internals — operate on already-normalized, correct unconditional), `:637` (immediate reward, kept unconditional by design — feeds dynamics CE), `:689` (gated), `:1266` (gated), `:1268` (post-norm guard, unconditional), `:1284` (gated), `:1286` (post-norm guard, unconditional), `:1297` (gated), `:1299` (post-norm guard, unconditional). The 4-gate set is complete; nothing missed.
- **Stage A (`make_dynamics_train_step`) is unaffected.** `:311-370` — Stage A uses `rewards` (clipped at `:637`) for the dynamics reward CE via `scalar_to_categorical(rewards)` (`:349`). No PopArt, no value target, no F2 surface. F2 is Stage-B only as expected.

## Inconclusive / out of scope

- **`post_popart` long-run stability.** Smoke is 1 epoch × 50 steps. The mechanism gate (rs200 must lift) and standard gate (rs100 must lift ≥ +3pp) require the actual server-side 3-seed × 2-cell × ~12h experiment. SPEC's smoke-passes / Δstd-widens evidence is necessary but not sufficient; the only way to validate the bridge from "PopArt sees the true distribution" to "Alpha rises" is the experiment itself.
- **Whether the early-epoch saturation (F5) interferes with the value head's optimisation trajectory in a non-recoverable way.** At rs200 with PopArt initialising from a single large-variance first batch, the value head sees a near-constant `td_target_norm ≈ ±10` for batch 1 then a sudden contraction. This could in principle bias the value head into a local minimum it doesn't escape, but only the run can tell. Worth watching `value_loss` shape over the first ~50 steps when the experiment runs.
- **Whether `post_popart` interacts badly with the auxiliary direction / rank / Bella heads.** All four heads (`direction_head` :1370+, `rank_head`, `bella_distill`, `bella_shape`) sit downstream of the same encoder/dynamics. F2 only changes the value-target normalization; the auxiliary heads' targets and weights are untouched. No direct interaction surface, but the value-loss / value-grad's contribution to the joint update changes magnitude under `post_popart`, which redistributes how the encoder is pushed. Probably negligible — the heads operate on stopped gradients per `:1252` — but cannot be ruled out without the run.
- **The `c2ad6f5` orphan hash in SPEC body is reachable via `git reflog` only.** On a fresh clone (no reflog), this hash is unresolvable. Whether that ever bites depends on how an agent reads the SPEC; flagged as F2 but the impact is purely "minor confusion if anyone tries `git show c2ad6f5`."
