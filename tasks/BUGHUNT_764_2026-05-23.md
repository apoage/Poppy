# BUGHUNT 764 — oracle-k CLI flag (commit 2ee38f7)

Read-only adversarial QA of the `--oracle-k` plumbing that shipped with smoke caveat (no live JAX exercised). Scope: `train_easy.py` argparse + override, `train_phase2.py` inheritance log, the path_solver kernel surface at k != 4, the dojo claim, and config-field invariants.

## Findings

### F1 (P2): `__post_init__` `oracle_k > 0` assertion is bypassed by CLI override
- `easy_config.py:158` — `assert self.oracle_k > 0` runs in `__post_init__` (so JSON-loaded configs and preset dataclasses are validated).
- `train_easy.py:3049-3051` — the CLI override is a direct attribute set (`config.oracle_k = args.oracle_k`) AFTER the dataclass is built. `__post_init__` does not re-run. There is no replacement validator on `args.oracle_k`.
- Consequence: `python train_easy.py --oracle-k 0`, `--oracle-k -1`, etc. silently install an invalid k. Failures then surface downstream as opaque JAX errors (e.g. `jax.lax.top_k(arr, k=0)` returns empty arrays; `top_k(arr, k=-1)` is undefined; `top_k(arr, k=100)` with 64 assets explodes), or — worse — succeed quietly with a degenerate oracle (k=0 → no trades, k=1 reverts to TASK_143/145 regime). The argparse declaration carries no `choices=` / range check.
- Compare: `--oracle-k 0` via a JSON config IS caught by `__post_init__`. The CLI path is the only soft spot.
- Fix (1-liner): guard at the override site or add a validator. E.g.
  ```python
  if args.oracle_k is not None:
      assert 0 < args.oracle_k <= config.n_assets, f"--oracle-k must be in (0, {config.n_assets}], got {args.oracle_k}"
      config.oracle_k = args.oracle_k
  ```
  Or pass `choices=[4, 8, 12]` since the sweep is closed-set. Or call `config.__post_init__()` after the override.

### F2 (P2): `e-dojo_v1.py` launcher does NOT forward `--oracle-k`
- `tools/orchestration/e-dojo_v1.py:1228-1236` (`DEFAULT_PARAMS`) and `:1254-1326` (`launch_branch` cmd builder) hardcode the exact set of CLI flags forwarded to `train_easy.py`: `--preset, --epochs, --steps-per-epoch, --batch-size, --n-envs, --buffer-size, --name, --output-dir, --no-latent-cache, --seed, --ar-max-blend, --bella/--invert-regime/--levels, --db-path, --periods-file, --lr, --start-date, --end-date, --assets-file, --oracle-multipass, --benchmark-every, --benchmark-gpu, --checkpoint`. No fallback `**kwargs → cmd.extend(...)`. `oracle_k` (or any kwarg not in the hand-rolled set) is silently dropped.
- The 764 commit message and task spec assert this is fine because "Phase-1 imprints are launched by calling `train_easy.py` directly (per TASK_729b / server SPEC convention)". Verified for 729b (`tasks/TASK_729b_WIDER_ENCODER.md:88-96` runs `python train_easy.py ...` directly). But:
  - The e-dojo file is alive, edited as recently as 2026-05-22 (same day as 764), and `launch_single_branch` (`:1661-1701`) drives `train_easy.py` for the single-GPU Phase-1 path. An operator who reaches for `python tools/orchestration/e-dojo_v1.py --run --single` (the only documented Phase-1 dojo entry — `tools/orchestration/CLAUDE.md` "Entry commands") will get k=4 with no error, voiding the experiment.
  - There is no defensive log in `train_easy.py` to confirm k after override (the log only fires when the CLI flag is explicitly set). So the void scenario is silent on both sides.
- Fix: either (a) add 2 lines to `e-dojo_v1.py` (`oracle_k` in DEFAULT_PARAMS + `if kwargs.get('oracle_k'): cmd.extend(['--oracle-k', str(kwargs['oracle_k'])])`), or (b) add an unconditional `logger.info(f"[CONFIG] oracle_k={config.oracle_k}")` to `train_easy.py:main()` after the override block, so the actual k is always visible in startup logs regardless of launch path.

### F3 (P2): Phase-2 inheritance log says "inherited" but reads dataclass default for old/missing keys
- `train_phase2.py:2580` — `logger.info(f"[TASK_764] oracle_k inherited from Phase-1 checkpoint = {config.oracle_k}")`. Placement (after lines 2570 `get_phase2_config(...)` / 2574 `Phase2Config(**filtered)`) is correct — config is always built before the log fires.
- But the log message overpromises. If the Phase-1 ckpt was written before the `oracle_k` field existed, or `config.json` was hand-edited and the key dropped, the ckpt dict's `oracle_k` is absent. Both branches then fall back to the `EasyConfig` dataclass default (`oracle_k: int = 4`, `easy_config.py:64`), and the log will say "inherited = 4" — exactly mimicking a healthy k=4 imprint. The very failure mode the log was added to catch (silent k=4 mismatch) is the one it cannot distinguish.
- Practical risk is low — every ckpt produced since TASK_666 has `oracle_k` in `config.__dict__` (saved via `easy_trainer.py:440`). But a 764P2 run pointed at a corrupted/edited `config.json` would still mislead.
- Fix (defensive): probe the key explicitly.
  ```python
  k_in_p1 = p1_config.get('oracle_k', '<MISSING — default 4>') if isinstance(p1_config, dict) else 'n/a'
  logger.info(f"[TASK_764] oracle_k from ckpt config = {k_in_p1}, Phase-2 will run with = {config.oracle_k}")
  ```
  Or hard-error if the key is missing from a ckpt whose epoch ≥ the TASK_666 commit threshold.

### F4 (P3): Argparse abbreviation could cause confusing errors with future `--oracle-*` flags
- `train_easy.py:2900` uses default argparse without `allow_abbrev=False`. With three `--oracle-*` flags (`--oracle-multipass`, `--oracle-mask-head`, `--oracle-k`), `--oracle-k 8` itself is unambiguous (no other flag starts with `oracle-k`), but `--oracle 8` or `--oracle-m` are ambiguous and argparse will error out with a prefix-conflict message that doesn't mention `--oracle-k` as one of the candidates clearly. Not a 764-introduced bug, but the new flag widens the surface. Cosmetic only.

### F5 (P3): `train_jax_fast.py:620` has hardcoded `k=4` for `compute_optimal_path`
- `train_jax_fast.py:620` — `compute_optimal_path(jnp.array(log_returns), k=4, method='greedy', transaction_cost=0.0)`. This is the Poppy training path (NOT Phase-1 imprint) and is explicitly out of scope for 764. Listed here only because the operator's spec mentioned "any unguarded path where the default applies?" — this is an unguarded k=4 in a sibling entry point. If TASK_764 expands beyond Phase-1, this is the second place to plumb the flag.
- The three function-signature defaults flagged by the 764 deep-dive (`train_easy.py:88, 188, 327`) are correctly identified as inert: every live call site (`train_easy.py:700, 1714, 1728, 1830, 1851, 1897, 2054, 2086`, plus the SegmentPool `oc.get('oracle_k', 4)` at `:703, :1007`) passes `k=self.config.oracle_k` or `oc.get('oracle_k', 4)` where the dict was built from the overridden config. Confirmed safe.

### F6 (informational): k changes the distribution of state-channel 32 (capacity)
- `train_easy.py:122-131` / `:231-238` — channel 32 = `n_active / k`. At k=4 with oracle picking exactly 4 every step (the canonical case), this channel is degenerate (always 1.0). At k=8 with oracle picking up to 8, the channel will carry actual information in [0, 1]. Not a bug, by design (`oracle_k > 0` allows any positive value), but a load-bearing distributional shift between k=4 and k=8/12 imprints. Encoders trained at one k are not interchangeable with the other through this channel alone — already implied by the 764 spec ("Phase 1 retrain breaks the imprint contract"). Worth flagging in the experiment notes.

## Verified clean

- **Override placement / ordering**: `train_easy.py:3049-3051` runs strictly before the `oracle_cfg` dict build at `:3157-3166`, before `config.save(...)` at `:3327`, and before `OnTheFlyGenerator(config, ...)` at `:3228`. The dict-built oracle config receives the overridden value. `config.json` written next to the checkpoint reflects the actual k used.
- **`default=None` invariant**: When `args.oracle_k is None`, the override is skipped — preset/`--config` value is preserved bit-identical. No downstream consumer sees `None`; `args.oracle_k` is only read inside the `if args.oracle_k is not None:` guard.
- **Phase-2 inheritance (when ckpt has the key)**: `Phase2Config(EasyConfig)` (`phase2_config.py:13-14`) inherits `oracle_k` via dataclass field; `get_phase2_config(...)` (`:297-307`) filters Phase-1 JSON to `EasyConfig.__dataclass_fields__` which includes `oracle_k`; the fallback branch (`train_phase2.py:2574-2575`) filters to `Phase2Config.__dataclass_fields__` which inherits `oracle_k`. Either path carries it through. `easy_trainer.py:440` writes `self.config.__dict__` into the ckpt, so the value round-trips.
- **`k_count` per-step normalization**: `path_solver.py:130` and `train_phase2.py:629` both compute `k_count` dynamically from the actual selection mask (`jnp.maximum(jnp.sum(new_mask), 1.0)` / `np.maximum(np.sum(oracle_sel, axis=-1), 1.0)`). Adapts to k automatically — no hardcoded /4.
- **`n_active / k` in `build_state_channels`**: uses the static-arg `k` (line 123, line 231 of `train_easy.py`), and every call site passes `k=self.config.oracle_k`. Correct per-call k.
- **JIT `static_argnames=['k', ...]`**: `path_solver.py:38, 182, 219, 342, 484, 580` and `train_easy.py:83, 181, 320` all declare `k` static. A new k value triggers a fresh JIT compile — slower first call, correct semantics.
- **`jax.lax.top_k(masked_returns, k=8)`**: valid for any k ≤ `n_assets`. The 64-asset universe permits k up to 64. No shape assumption breaks at k != 4 inside the oracle kernel (selections shape is `(T, n_assets)`, indices shape is `(T, k)` — k flows through generically).
- **No disk-cached oracle**: `train_easy.py:1005-1018` (`_precompute_oracle`) runs `greedy_lookahead_path` on the fly with the current k. No need for label-cache invalidation when k changes.
- **`oracle_cfg` dict construction order**: `train_phase2.py:452-490` builds its own `oracle_cfg` after `config` is loaded; reads `config.oracle_k` which has already been inherited. Independent of `train_easy.py`'s flow.
- **Phase-2 inheritance-log placement**: `train_phase2.py:2580` is unconditional (both `if/else` branches at 2570/2574 always assign `config`), runs before any further config mutation, fires once at startup. Visible.

## Inconclusive / out of scope

- **Live JAX behaviour at k=8/12**: read-only static analysis. Did not exercise `greedy_lookahead_path` / `build_state_channels` / `_build_model_state_trajectory_batched` at k=8 in a Python process. The kernels are generic in k by construction (every shape that depends on k uses the static-arg value), and `jax.lax.top_k` is documented to support any k ≤ array length, but a live smoke is the only way to fully rule out an XLA-level surprise (e.g. extreme VRAM spike at large k for `multipass_oracle_policy` × `n_passes`, or `lax.scan` unroll behaviour change). Recommend a single `python train_easy.py --preset medium --oracle-k 8 --epochs 1 --steps-per-epoch 5 --periods-file <small-file>` smoke on the workstation before the server sweep starts.
- **`oracle_k` vs `oracle_lookahead` relationship**: kernel-level they are independent (k ranks assets by lookahead-summed |return|; nothing constrains their ratio). Whether the *experimental hypothesis* (`project_bull_blindness.md`) requires lookahead to scale with k is a research question, not a code-correctness one.
- **`benchmark_easy.py` / `benchmark_oracle_vs_model.py`**: both read `config.oracle_k` from the loaded ckpt config (`benchmark_easy.py:506, 607, 973, 1122`; `benchmark_oracle_vs_model.py:239, 624`). They will follow the ckpt's k automatically, no plumbing needed. Out of scope but verified.
- **Whether the 764 experiment will actually launch via direct `python train_easy.py` rather than e-dojo**: organisational/operator question, not a code property. F2 covers the failure mode if the e-dojo path is reached.

## Summary

3 P2 findings (assertion bypass; e-dojo silent drop; inheritance-log false-positive on missing key), 2 P3 (argparse abbrev, sibling unguarded k=4 in `train_jax_fast.py`), 1 informational (channel-32 distributional shift between k values). Override placement, ordering, dict construction, Phase-2 inheritance, and the kernel's generic-in-k property all verified clean. None of the P2s block running the 764 sweep IF the operator launches Phase-1 directly with a sane `--oracle-k {4,8,12}`. P2 F1 and F2 are guardrail gaps that would only bite under operator error or path drift. F3 only bites if a `config.json` is corrupted/edited.
