# BUGHUNT 767 — action-space restructure (commit 7f41586)

Adversarial read-only review of TASK_767 — flag-gated drop of the two
limit-order actions (LimitSell=3, LimitBuy=4) from the Phase-2 320-dim
action space, leaving an effective 192-dim space. Code commit `7f41586`;
SPEC flip `14b26b4`. The agent's report claims canon (flag-OFF) is
bit-identical pre-767 and flag-ON masks correctly; smoke reported flag-ON
`limit_action_fraction=0.000`, canon `limit_action_fraction=0.398`.

**Verdict at a glance**: One **P0** correctness bug found in the
load-bearing mechanism (factored search Q→policy) — the `q_values.mean()`
centering step in `factored_search.py:_q_to_policy` collapses to a
float32-precision-loss trap when masked-action sentinels of `-1e9` enter
the mean. With `disable_limit_orders=True`, the per-asset mean drops to
~−4e8, the +4e8 shift exceeds the float32 ULP at that magnitude (≈32) for
typical Q values in [−20, 20], and all valid Q's collapse to the same
float32 value before softmax. The training target for the factored search
becomes **uniform across valid actions per asset** (e.g.
`[1/3, 1/3, 1/3, 0, 0]`), not Q-weighted. Action selection (`argmax`
directly on `q_values`, line 201) still correctly picks the highest-Q
action — so the smoke's "no NaN, limit_action_fraction=0.000" passes —
but the **policy training signal is degenerate**, teaching the policy
"random pick across buy/sell/hold per asset" rather than the best-Q
action. The mechanism gate (trade-count reduction) and any Alpha gain
would be tested under a sabotaged variant; a regression result would be
mis-attributed to "limit removal hurts" when the actual cause is the
masking implementation. Canon path is unaffected (action_mask is None,
the centering step has no -1e9 to amplify).

Two **P1** findings on related propagation surfaces (the eval-MCTS
per_asset decode tie-breaking and the joint-MCTS interior tree expansion
of unmasked recurrent priors — both pre-existing but newly load-bearing
under the 767 mask). One **P2** on the Stage-B → Stage-B config
inheritance path losing `disable_limit_orders` if a stray Phase-1
`config.json` sits next to a Phase-2 checkpoint. One **P2** on SPEC line
numbers ~30 lines stale due to TASK_769 insertions. **No P0 found on the
canon (flag-OFF) path** — bit-identity holds.

## Findings

### F1 (P0): factored search `_q_to_policy` mean-centering collapses to uniform when limit Q-values are masked to −1e9

- `mcts_trader/jax_agent/factored_search.py:194` — `q_values = jnp.where(mask_r.astype(bool), q_values, -1e9)` masks the two limit-action Q's per asset to −1e9.
- `mcts_trader/jax_agent/factored_search.py:128-131` — `_q_to_policy` then runs `q_centered = q_values - q_values.mean(axis=-1, keepdims=True)` followed by `jax.nn.softmax(q_centered / self.temperature)`.
- The agent's comment at `factored_search.py:182-189` correctly addresses the `-1e9` vs `finfo.min` trade-off for sum-overflow and softmax-tail (∑=−5e9 fits float32, softmax tail at exp(−1e9) underflows to 0). **It does not consider what the −1e9 entries do to the *valid* Q's via the mean step.**
- **Precision arithmetic (float32)**:
  - For a per-asset Q vector `[Q0, Q1, Q2, −1e9, −1e9]` with `Q_i ∈ [−20, 20]` (`reward + 0.95·value` from PopArt-denormalized supports):
    - `sum = Q0 + Q1 + Q2 − 2e9`. ULP at 2e9 ≈ 256, so `Q0+Q1+Q2 ∈ [−60, 60]` rounds out — `sum ≈ −2e9` exactly.
    - `mean = sum / 5 = −4e8`.
    - `q_centered[i] = Q_i − (−4e8) = Q_i + 4e8`. ULP at 4e8 = 32, so any `|Q_i| < 16` rounds to `4e8` exactly. Q's of magnitude 16–48 round to `4e8 ± 32`. **In practice the three valid q_centered entries collapse to the same float32 number.**
    - `q_centered[3,4] = −1e9 + 4e8 = −6e8` (exact).
  - `softmax([4e8, 4e8, 4e8, −6e8, −6e8] / T=1)`:
    - max = 4e8.
    - `exp(q_centered − max) = exp([0, 0, 0, −1e9, −1e9]) = [1, 1, 1, 0, 0]` (exp(−1e9) underflows in float32).
    - Normalized = `[1/3, 1/3, 1/3, 0, 0]` — **uniform across the three valid actions**.
- **Downstream impact**: this `policy_probs` IS the `mcts_visits` target returned to the trainer (`train_phase2.py:1928`). The factored-mode CE at `train_phase2.py:1216` trains `policy_logits` against this uniform-across-valid target. The oracle BC at `:1337` continues to teach the per-asset best-action, but its weight decays from `bc_start=0.05` to `bc_weight_min=0.03` while `exit_policy_weight=1.0`. So the dominant policy training signal (~95% of policy_loss) instructs the policy to output uniform across buy/sell/hold per asset, with the BC providing a weak corrective.
- **Why the smoke didn't catch it**:
  - `limit_action_fraction = _act_frac[3]+_act_frac[4]`. With the bug the valid uniform is `[1/3, 1/3, 1/3, 0, 0]` per asset → fraction on `{3,4}` is exactly 0 → smoke reports `0.000` (the expected "mechanism works" signal).
  - `mean_trade_rate = 1 − _act_frac[1]` would land at `1 − 1/3 = 0.667` for the flag-ON smoke, vs the canon's ~`1 − 0.30 ≈ 0.70`. Agent's smoke summary only reported `limit_action_fraction`, not `mean_trade_rate`, so the uniform-vs-Q-weighted distribution wasn't compared.
  - Smoke is 1 epoch — too short for the policy to converge to uniform under the buggy target; BC weight is still high, so the policy still looks "OK" in epoch 0.
- **Action selection still works**: `factored_search.py:199-204` does `argmax(q_values, axis=-1)` on the masked (un-centered) `q_values` to pick the per-asset action and the max-advantage asset. Since limit entries are −1e9 (far below any real Q), the argmax never picks 3 or 4 — `_actions` returned to the trainer is limit-free. **The bug is exclusively in the policy *target*, not the action *selection*.**
- **Canon path unaffected**: when `action_mask is None`, `q_values = jnp.where(...)` is skipped, no −1e9 enters the mean, `q_centered ≈ q_values` (mean ≈ 0, ULP at Q-scale ≈ 2e−6), Q diffs preserved. Confirmed bit-identical to pre-767 by trace inspection (`__call__` line 232-234 routes `action_mask=None` to a 3-arg JIT call; the `if action_mask is not None` branch at line 191 is dead Python).
- **Recommended fix** (in priority order):
  1. **Best**: remove the explicit centering — `softmax(q_values / T)` directly. JAX's softmax is max-stable, so subtracting the mean adds nothing for numerical stability; with −1e9 masks, the max-subtraction inside softmax already handles the dynamic range correctly (`exp(−1e9 − Q_max)` underflows to 0; valid Q's get `exp(Q − Q_max)`, full precision preserved).
  2. Compute the mean over valid actions only — `q_values.mean(axis=-1, where=valid_mask)` (requires `valid_mask` plumbed into `_q_to_policy`, which the function already accepts).
  3. Use a smaller mask sentinel like `−100.0` — still well below typical Q in `[−20, 20]` so masked-action softmax probability is `exp(−100) ≈ 3.7e-44` (effectively zero), but the mean stays in `[−40, 40]` so the centering shift is benign.
- **Verification path** (post-fix smoke): compare `mean_trade_rate` flag-ON vs canon. If canon ≈ 0.70 and flag-ON ≈ 0.50–0.60 (peaked toward learned-best actions), the fix worked. If flag-ON ≈ 0.667 (= 2/3), the bug is still present.
- **Severity rationale (P0)**: this is the load-bearing mechanism of the experiment (the SPEC explicitly calls factored search "the canonical Stage-B search"; the mechanism gate is trade-count reduction under that search). With this bug, the experiment cannot test the hypothesis it claims to — a regression result would be wrong-cause-attributed.

### F2 (P1): joint-MCTS interior action selection at depth ≥ 1 uses unmasked `recurrent_fn` prior_logits → tree spends compute expanding limit branches

- `mcts_trader/jax_agent/mctx_search.py:116` — the recurrent_fn returns `prior_logits=output['policy_logits']` (the raw, **unmasked** policy head output). No limit mask is applied to interior priors.
- `trader_env/lib/python3.10/site-packages/mctx/_src/action_selection.py:158-195` — `gumbel_muzero_interior_action_selection` computes `softmax(prior_logits + completed_qvalues)` and `argmax` over it (no `masked_argmax`, no `invalid_actions` at interior depth).
- `policies.py:90` — only the **root** action selection is masked (`masked_argmax(..., tree.root_invalid_actions * (depth == 0))`).
- Impact:
  - At depth ≥ 1, the tree can expand limit-action branches if their unmasked prior + Q is the highest. The value backups from these branches flow into the root's `completed_qvalues`, biasing the root Q-estimates that drive the final `action_weights = softmax(_mask_invalid_actions(prior + completed_q))`.
  - This is an inefficiency (wasted simulations on dead-end branches), not a hard correctness break — the final root `action` and `action_weights` are correctly masked. But the **value-tree estimate** at root incorporates limit-branch backups, which can bias the visit distribution toward branches that happen to be near limit subtrees.
  - For 767, this means the joint-MCTS training-time visit distribution (when `use_factored_search=False`) is not perfectly limit-clean — the visits *to limit actions at root* are zero, but the visits *to other valid actions* are influenced by the (possibly mis-estimated) value of limit subtrees.
- This is an existing mctx behavior, **newly load-bearing** under 767's mask: pre-767 nobody cared that interior limit expansions happened because limits were valid training targets; post-767, every limit-branch simulation is a wasted compute slot that could have gone to a valid (sell/hold/buy) branch.
- **Recommended fix**: pass a limit-mask through `_recurrent_fn` to mask the recurrent prior_logits. This requires plumbing the mask into the closure used by mctx and is invasive — likely not worth it given (a) the SPEC's canonical search is factored, not joint, and (b) joint MCTS only runs at `sims=32` (training) and `sims=16` (eval), so the wasted simulation count is bounded.
- **Severity rationale (P1)**: degrades joint MCTS efficiency under 767 but doesn't break correctness of the final policy target. The SPEC's promotion gate is eval-MCTS sims=16 joint — the eval is affected by this inefficiency, but the bias direction is unclear (limit-branch value estimates could be high or low; the visit distribution shifts could go either way). Mitigation: increase sims to compensate. **No fix recommended for the 767 launch**, but worth noting that joint MCTS is not "limit-free deep" — only "limit-free at root".

### F3 (P1): eval-MCTS per_asset decode argmax can return SELL (index 0) for un-visited assets when policy_probs valid mass collapses to identical small values

- `tools/benchmark_easy.py:421-422` — `per_asset = policy_probs.reshape(B, n_assets, 5); return np.argmax(per_asset, axis=-1)`.
- `policy_probs` from mctx is `softmax(_mask_invalid_actions(root.prior_logits + completed_qvalues, invalid_actions))` — for limit actions it's exactly 0 (mctx uses `finfo.min` masking → softmax → 0). For valid actions on an asset NOT chosen by the joint MCTS, the prior+Q values are small and largely undifferentiated (visit counts are near-zero, completed_qvalues fall back to mix-value).
- For un-visited assets, the per-asset softmax slice is `[p_sell, p_hold, p_buy, 0, 0]` where `p_sell, p_hold, p_buy` are tiny and may differ only in the 6th-7th decimal place. `np.argmax([a, b, c, 0, 0])` returns the first index of the max — with floating-point ties or near-ties, this is biased toward **index 0 (SELL)** because numpy's `argmax` returns the first occurrence of the max.
- This is pre-existing behavior of `per_asset` decode under joint MCTS — not introduced by 767. **But 767 makes it worse**: with the limit channel removed, the policy mass that previously diffused across 5 actions now diffuses across 3, and the un-visited-asset tie-breaking is exercised on every batch (the joint MCTS still picks one asset; the other 63 are tie-breaking targets). If `eval_mcts_decode='per_asset'` is ever used on a 767 checkpoint, the per-asset decode will produce a SELL-biased action mask on 63/64 assets.
- **Mitigation**: the SPEC default and the 767 promotion gate both specify `eval_mcts_decode='joint'`, which does NOT exercise this path (joint decode returns the single MCTS-picked action with all other assets HOLD). So in practice the 767 launch is safe. **Risk surface only**: a downstream operator running with `--eval-mcts-decode per_asset` against a 767 checkpoint would see severe SELL bias on un-visited assets.
- **Recommended fix**: in `_mcts_decode_actions` per_asset mode, default un-visited assets to HOLD (index 1) instead of using argmax over near-zero probs. Detect via a probability threshold (e.g., `max(per_asset) > 1e-6 ? argmax : 1`).
- **Severity rationale (P1)**: the bug doesn't fire under the SPEC's default eval-decode, but is one CLI flag away from a catastrophic eval. Not 767-specific but newly relevant.

### F4 (P2): Stage-B → Stage-B resume drops `disable_limit_orders` if a stray Phase-1 `config.json` exists next to the checkpoint

- `train_phase2.py:2569-2575`:
  ```python
  p1_config_path = ckpt_dir / 'config.json'
  if p1_config_path.exists():
      config = get_phase2_config(str(p1_config_path))   # filters to EasyConfig fields only
  else:
      config = Phase2Config(**{k: v for k, v in p1_config.items()
                               if k in Phase2Config.__dataclass_fields__})  # Phase2 fields included
  ```
- `phase2_config.py:297-307` — `get_phase2_config` filters input to `EasyConfig.__dataclass_fields__`. **`disable_limit_orders` is a Phase2Config-only field**, NOT in EasyConfig, so it gets dropped on this code path.
- Normal Stage-A → Stage-B resume flow: Stage-A's checkpoint dir has no `config.json` (only `train_stage_b` writes `stage_b_config.json` — `:1805`), so the `else` branch runs and `disable_limit_orders` is preserved from the Phase-2 metadata dict.
- **The bug-trigger path**: a user manually copies a Phase-1 `config.json` next to a Phase-2 Stage-A checkpoint (or the deploy script does this for some reason). Then resume silently loses the flag, and Stage B trains with `disable_limit_orders=False` even though Stage A had it on.
- Inverse: a user does this and the flag-loss goes unnoticed because Stage A's checkpoint config had `disable_limit_orders=True` but the CLI override at `:2630-2631` (`if args.disable_limit_orders: config.disable_limit_orders = True`) is one-way — there is no `--no-disable-limit-orders` option in `train_phase2.py` (unlike `tools/benchmark_easy.py` which uses `BooleanOptionalAction`). So once the flag is lost via the EasyConfig filter, it cannot be force-re-enabled without changing code.
- **Operator detection**: the training preamble would log `TASK_767: limit orders DISABLED — MCTS action space 64x5=320 → effective 64x3=192…` (`train_phase2.py:1758-1761`) only when the flag is on. So a Stage B that silently dropped the flag would NOT show that log line, which a careful operator can use as a sanity check.
- **Recommended fix**: `phase2_config.py:get_phase2_config` should also accept Phase2Config-only fields when loading a Phase-2 (not Phase-1) config; or, more conservatively, the call site at `train_phase2.py:2570` should be `Phase2Config.__dataclass_fields__` not `EasyConfig.__dataclass_fields__`. Either way: also add `--no-disable-limit-orders` to `train_phase2.py` parse_args (using `BooleanOptionalAction` like benchmark_easy does) so the flag can be force-toggled either way.
- **Severity rationale (P2)**: the SPEC's intended workflow (Phase 1 → Phase 2 with `--disable-limit-orders` at CLI each time) avoids this path; a careful operator catches the missing log line. But it's an unguarded silent-failure path that a future agent could trip over.

## Inconclusive / out of scope

- **Whether XLA's algebraic simplifier eliminates the `(q − q.mean()) → softmax` mean-shift**: softmax is shift-invariant (`softmax(x + c) = softmax(x)` for scalar c), so mathematically `softmax(q − q.mean())` ≡ `softmax(q)`. If XLA performs this simplification at HLO-pass time, F1 would NOT manifest (the explicit mean-subtract would be optimized away before float32 evaluation). I do not have evidence that XLA performs this specific pattern-match (it would require recognizing "subtract a constant computed from the reduction axis is dead before a softmax over the same axis"); typical XLA simplifications are more local. **Empirical verification needed**: a 3-epoch flag-ON smoke that logs `mean_trade_rate` would distinguish — uniform-by-bug gives `0.667`, learned-from-Q gives a value driven by the policy's learned trade rate (likely 0.5–0.7 depending on training state).
